# Software Supply Chain Security

How supply chain attacks actually happen, the SLSA framework, dependency pinning as a first line of defense, and verifying artifact provenance. This file covers the broad supply chain problem; CI-specific instances of it (SHA-pinning third-party GitHub Actions/CircleCI orbs) are covered where the CI tooling itself is documented, not repeated here.

---

## 1. Anatomy of a Supply Chain Attack

A supply chain attack doesn't target your application directly — it targets something **your application trusts and pulls in automatically**: a dependency, a CI runner, a build tool, a base image. The attacker's code then rides along into your build and gets deployed with your legitimate release, under your own signature/authority.

### Scenario: a compromised dependency

```
1. Attacker gains publish access to a popular open-source package
   (stolen maintainer credentials, a social-engineered maintainer handover,
   or a typosquatted package name close to a real one)
        |
        v
2. Attacker publishes a new version with malicious code hidden in a
   post-install script or an obfuscated code path
        |
        v
3. Your dependency manager (npm/pip/etc.) auto-resolves to the new version
   on the next `npm install` — because your lockfile either doesn't pin it
   exactly, or the lockfile itself gets regenerated in CI
        |
        v
4. Your CI pipeline builds the app WITH the malicious code included,
   using your own build credentials and signing identity
        |
        v
5. The resulting artifact is legitimately signed/deployed by YOUR pipeline —
   nothing downstream (image scanner looking for known CVEs, admission
   controller checking your signature) has any reason to flag it, because
   structurally it IS your real, legitimately-built artifact — it just
   contains attacker code
```

### Scenario: a compromised CI runner

```
1. Attacker compromises a self-hosted CI runner (unpatched host, exposed
   Docker socket, a malicious PR that runs on a runner with access to
   secrets — see the pull_request_target risk noted in this repo's
   GitHub Actions workflow-syntax notes)
        |
        v
2. Attacker's job runs with the SAME credentials your legitimate build
   jobs use — registry push tokens, signing keys/OIDC identity, deploy
   credentials
        |
        v
3. Attacker injects malicious code into the next real build (modifies a
   build script, replaces a build tool binary in a shared runner cache)
   OR pushes a malicious artifact directly using the stolen credentials
        |
        v
4. The malicious artifact is published/deployed as if it came from your
   trusted pipeline, because — again — it actually did
```

The common thread: **supply chain attacks are dangerous specifically because they inherit your own trust.** They don't need to defeat your scanners or your signature verification — they get inside the boundary those controls are meant to protect and come out the other side looking legitimate.

## 2. SLSA — Supply-chain Levels for Software Artifacts

SLSA is a framework of increasing maturity levels describing how much you can trust that an artifact was built the way it claims to have been built — not a single tool, but a set of practices you can audit against.

| Level | Roughly means | Example practice |
|---|---|---|
| **SLSA 1** | Build process is documented and produces provenance (a record of how it was built) | CI produces a build log / provenance file, even if unsigned and self-asserted |
| **SLSA 2** | Provenance is generated by a hosted build service and signed | GitHub Actions / GitLab CI generating signed attestations automatically, not a developer's laptop |
| **SLSA 3** | Build process is hardened against tampering — isolated, ephemeral build environments, provenance is non-forgeable | Ephemeral CI runners (fresh VM per build, no persistence between builds an attacker could poison), stronger isolation between build steps |
| **SLSA 4** | Two-person review of all changes, hermetic/reproducible builds | Every change requires independent review before merge; the build has no unpinned external inputs at all |

The practical value isn't "achieve SLSA 4 everywhere" — most teams aren't there and don't need to be for every artifact. It's a **shared vocabulary and checklist** for reasoning about how much a given build pipeline can be trusted, and where the concrete gaps are (self-hosted, persistent runners with no isolation between jobs is a common SLSA-3-blocking gap, for instance).

## 3. Dependency Pinning and Lockfiles

The single cheapest, highest-leverage defense against the "auto-resolves to a malicious new version" scenario in §1 is simply **not letting dependency resolution be a moving target**.

```bash
# Without a lockfile, this can resolve to a DIFFERENT version tomorrow than it did today —
# including a version published minutes ago by an attacker
npm install

# With a committed lockfile (package-lock.json / yarn.lock / pnpm-lock.yaml),
# installs are reproducible: exact versions, exact resolved integrity hashes
npm ci    # installs EXACTLY what's in the lockfile, fails if package.json and lockfile disagree
```

```
# package-lock.json entry — pinned to an exact version AND a content hash,
# so even a same-numbered "re-publish" of a version would be detected
"lodash": {
  "version": "4.17.21",
  "resolved": "https://registry.npmjs.org/lodash/-/lodash-4.17.21.tgz",
  "integrity": "sha512-v2kDEe57lecTulaDIuNTPy3Ry4..."
}
```

Lockfiles solve the *unintentional drift* problem (a transitive dependency silently bumping) but don't by themselves stop a **new, deliberately malicious release of a package you explicitly upgrade to** — that's where SCA scanning (see [sast-dast-and-code-scanning.md §3](sast-dast-and-code-scanning.md)) and a deliberate review process for dependency bumps (not just auto-merging every Dependabot PR without looking) come in as the next layer.

## 4. Verifying Artifact Provenance — Attestations

An **attestation** is a signed statement asserting a fact about an artifact — most commonly, "this exact artifact digest was built from this exact source commit, by this exact build pipeline, at this time." This connects directly to the cosign/Sigstore signing workflow covered in [container-and-image-security.md §4](container-and-image-security.md) — signing proves *who* published the artifact; provenance attestations go further and prove *how* it was built.

```bash
# cosign can attach a signed SLSA provenance attestation to an image, not just a signature
cosign attest --predicate provenance.json --type slsaprovenance myregistry/myapp:1.4.0

# verify the attestation before deploy — checks both the signature AND the claimed build process
cosign verify-attestation \
  --type slsaprovenance \
  --certificate-identity=https://github.com/your-org/your-repo/.github/workflows/build.yml@refs/heads/main \
  --certificate-oidc-issuer=https://token.actions.githubusercontent.com \
  myregistry/myapp:1.4.0
```

A deploy-time policy can then require not just "is this signed by someone" but "was this built by our exact CI workflow, from our exact repo" — meaningfully narrowing what counts as a trustworthy artifact versus what an attacker with *some* valid signing capability (e.g., a compromised but differently-scoped identity) could produce.

## 5. Third-Party CI Plugins/Actions/Orbs — the CI-Specific Instance of This Problem

Every third-party GitHub Action, CircleCI orb, or similar CI plugin is itself a dependency — it runs arbitrary code with access to your job's environment, including secrets. The exact same "auto-resolves to a new, possibly malicious version" risk from §1 and §3 applies directly, and the mitigation is the same idea (pin to an immutable reference, don't trust a mutable tag):

- **GitHub Actions**: pin third-party actions to a full commit SHA rather than a mutable tag like `@v4` — the full reasoning, syntax, and Dependabot-driven update pattern is covered in [GitHub Actions actions-and-marketplace.md §3](../Continuous%20Integration/GithubActions/actions-and-marketplace.md).
- **CircleCI**: pin orbs to an exact version (`orb@1.2.3`) rather than a floating range — covered in [CircleCI orbs-and-reusability.md](../Continuous%20Integration/CircleCI/orbs-and-reusability.md).

This file won't repeat those mechanics — the point here is just to name it explicitly as **the same supply chain trust problem as §1**, applied to your build tooling instead of your application's runtime dependencies. A compromised Action/orb is functionally identical to a compromised npm package: it executes with your pipeline's trust and credentials the moment it's pulled in.

## 6. Real-World Pattern (Conceptual)

Two widely-known public examples illustrate the general pattern, without needing incident-specific detail here:

- **SolarWinds (2020)**: attackers compromised the build infrastructure itself (not a public dependency), injecting malicious code into a legitimately signed software update — the build environment scenario from §1, at large scale, against a widely-trusted vendor.
- **Log4Shell (2021, `CVE-2021-44228`)**: not an intentional supply chain attack, but a vivid demonstration of the same underlying exposure — a single vulnerability in an extremely widely-used transitive dependency (Log4j) meant a huge fraction of the industry's software was suddenly critically vulnerable through code most teams didn't even know they depended on. This is exactly why SBOMs (see [container-and-image-security.md §3](container-and-image-security.md)) matter: teams with SBOMs could answer "are we affected" in minutes by grepping; teams without one had to manually audit every service.

The lesson from both, generalized: **your actual attack surface includes everything your build and runtime trust, transitively — not just the code your team wrote.** Every control in this file (pinning, SBOMs, signing, provenance, SLSA-style build hardening) exists to make that transitive trust visible and verifiable instead of implicit.
