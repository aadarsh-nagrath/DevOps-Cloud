## Junior Level (0–2 yrs)

### 1. What is Continuous Integration (CI), and what problem does it solve?
CI is the practice of frequently merging code changes into a shared branch (often several times a day) with each merge automatically triggering a build and test run. It solves "integration hell" — the pain of discovering conflicts and breakages only after weeks of divergent parallel work — by catching integration problems within minutes of them being introduced, when they're cheapest to fix.

### 2. What's the difference between Continuous Delivery and Continuous Deployment?
Both extend CI by automatically building, testing, and packaging every change so it's *always* in a releasable state. **Continuous Delivery** stops just short of production — a human still clicks a button to actually release. **Continuous Deployment** removes that manual gate entirely — every change that passes the pipeline is automatically released to production with no human approval step. The distinction is specifically about that final "deploy to prod" gate, not about how automated everything before it is.

### 3. What is a CI/CD pipeline, and what are its typical stages?
A pipeline is an automated, ordered sequence of stages a code change passes through from commit to (potentially) production. Typical stages: checkout source, install dependencies, lint/static analysis, build/compile, run unit tests, run integration tests, build an artifact (e.g. a Docker image), security/vulnerability scan, publish the artifact to a registry, and deploy to one or more environments — often with manual or automated approval gates between environments.

### 4. What is a build artifact, and why store it in a registry rather than rebuilding it for each environment?
An artifact is the packaged, deployable output of a build (a Docker image, a `.jar`/`.whl`/`.zip`, a compiled binary). You build it once and promote the *exact same* artifact through environments (dev → staging → prod) rather than rebuilding at each stage, because rebuilding risks subtle differences (a dependency version that resolved differently, a flaky build step) between what you tested and what you actually ship — "build once, deploy many times" is a foundational CI/CD principle.

### 5. What's the difference between a build trigger on "push" vs. on a "pull request"?
A push trigger runs the pipeline whenever commits land on a specific branch (often used for `main`, to build/deploy after merge). A pull-request trigger runs the pipeline against the *proposed* merge of a feature branch into its target, before merging — used to validate changes (tests, linting) and give reviewers confidence *before* code is merged, catching problems earlier than a push-only trigger would.

### 6. What is a "secret" in a CI/CD system, and why shouldn't you hardcode credentials in a pipeline config file?
A secret is sensitive data (API keys, database passwords, cloud credentials) a pipeline needs at runtime. Hardcoding it directly in a pipeline YAML/Jenkinsfile commits it to source control, where it's visible to anyone with repo access (including in the file's history, even if later removed) and often gets copy-pasted into forks/logs. CI platforms provide dedicated encrypted secret stores (GitHub Actions Secrets, GitLab CI/CD Variables marked "masked/protected," Jenkins Credentials) that inject secrets into the pipeline environment at runtime without ever exposing the raw value in the repository.

### 7. What's the difference between a CI "job" and a "stage" (or "step")?
Terminology varies by tool, but generally: a **pipeline** is the whole automated process; a **stage** is a logical phase of it (e.g. "test," "build," "deploy"); a **job** is a unit of work within a stage that runs on a single runner/agent (jobs within the same stage often run in parallel); and a **step** (or "task") is an individual command/action within a job, executed sequentially.

### 8. What is a "runner" or "agent" in a CI system?
A runner/agent is the actual machine (or container) that executes a pipeline's jobs — it checks out the code, runs the defined commands, and reports results back to the CI server/platform. Runners can be hosted by the CI provider (GitHub-hosted runners, GitLab SaaS runners) or self-hosted (your own VMs/Kubernetes pods registered to run jobs) — self-hosting is common when you need specific hardware (GPUs), network access to internal resources, or to control cost/compliance.

### 9. Why do teams cache dependencies (e.g. `node_modules`, pip packages) in CI, and what's the risk of caching incorrectly?
Reinstalling all dependencies from scratch on every single run can take minutes and hit external registries repeatedly, slowing every pipeline run and adding flakiness/rate-limit risk. Caching a dependency directory keyed by a hash of the lockfile (`package-lock.json`, `requirements.txt`) lets unchanged dependencies be restored instantly instead of reinstalled. The risk: caching too broadly or with a stale/incorrect cache key can silently restore outdated or incompatible dependencies, producing a build that "passes" against cached artifacts but wouldn't build cleanly from scratch — cache keys should be tied precisely to whatever determines the cache's validity (lockfile hash, not just branch name).

### 10. What does it mean for a test suite (or a pipeline) to be "flaky," and why is it a serious problem?
A flaky test/pipeline fails intermittently without any actual code change — due to timing issues, shared test state, external service dependencies, or race conditions in the test itself. It's a serious, compounding problem because once a team learns to expect and re-run flaky failures, they stop trusting red pipeline status at all, and start reflexively re-running/ignoring failures — which is exactly the moment a *real* failure gets waved through, defeating the entire purpose of CI as a safety net.

## Mid Level (2–5 yrs)

### 11. What is a Jenkinsfile, and what's the difference between Declarative and Scripted pipeline syntax?
A Jenkinsfile defines a pipeline as code, checked into source control alongside the application (rather than configured through Jenkins' UI). **Declarative** syntax (`pipeline { agent {} stages {} }`) is structured, opinionated, easier to read/validate, and is the modern recommended default. **Scripted** syntax is raw Groovy (`node { stage('Build') { ... } }`), more flexible/powerful for complex conditional logic but harder to read, lint, and maintain — most teams use Declarative and drop into a `script { }` block only for the specific bits of logic Declarative syntax can't express cleanly.

### 12. In Jenkins, what's the difference between a Freestyle project and a Pipeline project, and why has the industry moved toward Pipeline-as-code?
A Freestyle project is configured entirely through Jenkins' web UI — build steps, triggers, post-build actions all live as Jenkins server configuration, not in version control. A Pipeline project's entire definition lives in a Jenkinsfile in the repository itself — reviewable via pull request like any other code change, versioned alongside the app it builds, reproducible by re-checking-out any historical commit, and not dependent on manually replicating UI clicks if Jenkins itself needs to be rebuilt — which is why Pipeline-as-code is the standard recommended approach today.

### 13. What are Jenkins agents/nodes, and what's the difference between a permanent agent and a dynamically-provisioned one (e.g. via Kubernetes plugin)?
An agent is a machine that executes Jenkins build steps (the Jenkins "controller"/master schedules work and serves the UI, but production setups avoid running builds directly on the controller). A permanent agent is a long-lived, manually registered machine — simple, but idle capacity is wasted and it can accumulate state/drift across builds. A dynamically-provisioned agent (via the Kubernetes plugin, spinning up a fresh Pod per build, or cloud plugins spinning up ephemeral VMs) starts clean for every single build (eliminating cross-build contamination) and scales capacity to zero when idle — the preferred pattern for cost and build hygiene at scale.

### 14. Explain GitHub Actions' core building blocks: workflow, job, step, and action.
A **workflow** is a YAML file in `.github/workflows/` defining automation triggered by events (push, PR, schedule, manual dispatch). A workflow contains one or more **jobs**, which by default run in parallel on separate runners (unless you declare `needs:` dependencies between them to sequence them). Each job runs a sequence of **steps**. A step either runs a shell command directly, or invokes an **action** — a reusable, packaged unit of automation (from the Marketplace, a public/private repo, or a local path) that can take inputs and produce outputs.

### 15. What's the difference between `on: push`, `on: pull_request`, and `on: workflow_dispatch` in GitHub Actions?
`push` triggers on commits pushed to matching branches/tags. `pull_request` triggers when a PR is opened/updated against matching branches, running against the *merge* of the PR branch into its target (important: secrets are restricted/unavailable by default on `pull_request` from forks, specifically to prevent a malicious fork PR from exfiltrating your secrets — `pull_request_target` runs with the base branch's permissions/secrets instead, which is powerful but requires care to avoid running untrusted fork code with elevated access). `workflow_dispatch` allows manually triggering a workflow from the UI/API, optionally with input parameters — commonly used for manual deploy buttons.

### 16. What is a GitHub Actions "matrix build," and why use one?
`strategy.matrix` runs the same job multiple times with different variable combinations (e.g. multiple OS versions × multiple language runtime versions) in parallel, without duplicating the job definition — e.g. testing a library against Node 18/20/22 on Ubuntu/macOS/Windows in one concise block, generating 9 parallel jobs from a handful of lines of YAML.

### 17. How do reusable workflows (`workflow_call`) differ from composite actions in GitHub Actions?
A **composite action** bundles multiple steps into a single reusable *step* that can be dropped into any job — good for a small, self-contained sequence of commands used across many workflows. A **reusable workflow** (invoked via `uses: org/repo/.github/workflows/file.yml@ref` under `jobs.<id>.uses`, called with `workflow_call`) lets you reuse an entire *workflow* (potentially with multiple jobs, matrix strategies, secrets/inputs passed in) — the right tool when you want to standardize a whole build-test-deploy pipeline shape across many repositories, rather than just one reusable step.

### 18. What is `GITHUB_TOKEN`, and why does its default permission scope matter for security?
`GITHUB_TOKEN` is an automatically-generated, workflow-run-scoped credential GitHub injects into every Actions run, used for the workflow to authenticate back to the repository's API (commenting on a PR, creating a release, pushing a tag) without needing a manually managed personal access token. Its permissions default to fairly broad read/write access unless explicitly restricted via the `permissions:` key — the security best practice is to set `permissions: {}` (or minimal explicit grants) at the workflow or job level rather than relying on the (historically broader) repository-wide default, following least-privilege, especially important because a compromised or overly-permissive `GITHUB_TOKEN` combined with a supply-chain-compromised third-party action is a realistic attack path.

### 19. Why is pinning GitHub Actions to a commit SHA (instead of a tag like `@v4`) considered a security best practice?
A tag like `@v4` is mutable — the maintainer (or an attacker who compromises their account/repo) can move that tag to point at different, potentially malicious code at any time, and every workflow using `@v4` would silently pull the new code on its next run. Pinning to a full commit SHA (`actions/checkout@8f4b7f...`) guarantees the exact, immutable code that runs, regardless of what the tag is later moved to — tools like Dependabot can still keep SHA-pinned actions updated deliberately (via PRs you review), rather than trusting automatic, invisible updates.

### 20. What's the difference between GitLab CI's `.gitlab-ci.yml` and Jenkins' Jenkinsfile at a conceptual level, and what is a GitLab "runner"?
Conceptually similar — both are pipeline-as-code files checked into the repo. GitLab CI's YAML is purely declarative (no scripted/Groovy escape hatch like Jenkins), organized around `stages:` (ordered phases) and jobs assigned to a stage that run in parallel within it. A GitLab Runner is the equivalent of a Jenkins agent — the process that actually executes job scripts, which can run in `shell`, `docker`, or `kubernetes` executor modes, self-hosted or using GitLab.com's shared runners.

### 21. How do you pass artifacts (build outputs) from one job to another within the same pipeline?
Nearly every CI platform supports explicit artifact passing between jobs in the same pipeline run: GitHub Actions' `actions/upload-artifact` + `actions/download-artifact`, GitLab CI's `artifacts:` key (automatically available to later stages), Jenkins' `stash`/`unstash` (within one pipeline run) or the Archive Artifacts post-build step (for longer-term storage). This is necessary because each job typically runs on a fresh, isolated runner/workspace with no filesystem continuity between jobs by default.

### 22. What are deployment environments/gates, and how do you implement a manual approval step before deploying to production?
An "environment" in CI/CD platforms (GitHub Environments, GitLab Environments) represents a deploy target (staging, production) that can have protection rules attached — required reviewers who must approve before a job targeting that environment proceeds, wait timers, or restricting which branches/tags can deploy to it at all. This gives you an auditable, enforced manual gate (who approved, when) without needing a bespoke external approval system bolted onto the pipeline.

### 23. What's the difference between a blue-green deployment and a canary deployment, from a CI/CD pipeline's perspective?
Both are strategies for rolling out a new version safely, orchestrated by the deployment stage of a pipeline (often via the underlying platform — Kubernetes, a load balancer, a service mesh — rather than the CI tool itself). **Blue-green** keeps two full, identical environments; the pipeline deploys the new version entirely to the idle one, validates it, then atomically switches traffic over — instant rollback by switching back. **Canary** gradually shifts a small percentage of *live* traffic to the new version, monitoring error rates/metrics, and progressively increases that percentage (or aborts and rolls back) based on observed health — catching problems with real traffic at limited exposure, at the cost of more complex traffic-splitting and longer rollout time. (See the dedicated [Deployment Strategies](../Deployment) notes for full depth.)

### 24. How would you speed up a CI pipeline that takes 40 minutes and is slowing the whole team down?
Systematically: parallelize independent jobs/test suites (splitting a monolithic test run across multiple parallel runners/shards); cache dependencies and, where supported, incremental build outputs (compiler/build-tool caches, not just package manager caches); use `paths`/`rules`/path-filtering to skip jobs entirely when they're irrelevant to what changed (e.g. skip frontend tests on a backend-only change in a monorepo); right-size runner hardware (a slow, undersized shared runner is a common, easily-fixed bottleneck); trim genuinely unnecessary steps (redundant re-checkouts, verbose/unneeded scanning on every single push rather than on PR/merge only); and measure first with the CI platform's own timing breakdown per step, rather than guessing which stage is actually the bottleneck.

## Senior Level (5+ yrs)

### 25. Design a CI/CD pipeline architecture for a company running dozens of microservices across multiple teams, covering standardization vs. team autonomy.
Provide a small number of centrally-maintained, versioned reusable pipeline templates (GitHub reusable workflows, GitLab CI `include:` templates, or shared Jenkins Pipeline libraries) covering the common shape (lint → test → build → scan → publish → deploy) with well-defined extension points, rather than either forcing one rigid pipeline on every team (kills autonomy, breaks on legitimate edge cases) or letting every team hand-roll their own from scratch (massive duplicated effort, inconsistent security/quality gates, and a maintenance nightmare when a company-wide policy change — like a new required security scan — needs to land everywhere). Centralize genuinely cross-cutting, non-negotiable concerns (secret scanning, dependency vulnerability gates, required approvals for production deploys, SBOM generation) in the shared template layer so they can't be silently opted out of, while leaving service-specific build/test logic to each team within that shared shape — and version the shared templates so teams can adopt updates on their own schedule rather than being broken by an unannounced central change.

### 26. How do you secure a CI/CD pipeline against supply-chain attacks — both from third-party actions/plugins and from the pipeline's own privileged access to production?
Treat the CI system itself as a high-value target, since it typically holds credentials to deploy to production, sign artifacts, and access source code — a compromised pipeline is often a more direct path to "own everything" than compromising any single service. Concrete controls: pin all third-party actions/plugins to an immutable reference (commit SHA, not a mutable tag) and restrict which actions/plugins are even allowed to run (GitHub Actions' allow-listing, Jenkins Script Security); apply least-privilege scoped credentials per-pipeline/per-environment rather than one broad "CI service account" with access to everything; separate the *build* stage (which may run untrusted-ish code — dependency install scripts, test code) from the *deploy* stage's credentials, so a malicious dependency executed during `npm install` can't directly reach production deploy credentials; require signed commits/protected branches feeding into deploy-capable pipelines so an attacker can't just push directly to trigger a malicious deploy; and audit/alert on pipeline configuration changes themselves (a modified Jenkinsfile or workflow YAML that adds a new external destination for artifacts/secrets is itself a strong compromise signal worth monitoring, not just monitoring runtime production behavior).

### 27. What's your strategy for testing CI/CD pipeline configuration itself (the Jenkinsfile/workflow YAML) before it reaches production usage?
Pipeline-as-code is still code and benefits from the same discipline: lint pipeline YAML/Jenkinsfiles in CI (`actionlint` for GitHub Actions, GitLab's CI Lint API, Jenkins' `Replay`/declarative linter), test complex custom logic (a shared Jenkins Pipeline library's Groovy code, a composite action's script) with actual unit tests rather than only validating it by triggering real pipeline runs, and stage pipeline changes themselves through a lower-risk path first (a feature-branch workflow run, or a non-production Jenkins instance/GitLab project) before merging changes that affect production-deploying pipelines — treating "the pipeline broke and now nothing can deploy, including the fix" as a real failure mode to design around (e.g., keeping a manual/break-glass deploy path that doesn't depend on the primary automated pipeline working).

### 28. How would you design deployment pipelines to support fast, safe rollback — not just fast forward deployment?
Rollback needs to be a first-class, tested pipeline capability, not an afterthought improvised during an incident. Concretely: always deploy immutable, uniquely-tagged artifacts (never overwrite/redeploy a mutable `:latest` tag) so "redeploy the previous artifact" is unambiguous and instant; keep deployment manifests/config for the *previous* N releases readily available (GitOps repositories are naturally good at this, since the previous state is just an earlier Git commit — `git revert` the deploy manifest change and let the GitOps reconciler apply it); prefer deployment strategies with inherently fast rollback (blue-green's instant traffic-switch-back, vs. a rolling deployment which must roll forward *again* with the old version, taking similar time to the original rollout); and — critically — actually rehearse rollback (game days, chaos engineering exercises) rather than assuming the rollback path works because it looks correct on paper; a rollback mechanism that's never been exercised is a common source of "the rollback itself failed" during a real incident.

### 29. How do you approach CI/CD for a monorepo housing many independently-deployable services, versus a polyrepo (one repo per service)?
A monorepo needs path/dependency-graph-aware pipeline logic (via a build tool like Bazel/Nx/Turborepo, or hand-built path-filtering) so a change to one service doesn't trigger a full rebuild/redeploy of every service in the repo — without this, CI time and blast radius both scale badly as the monorepo grows. It gains simpler cross-service atomic changes (one PR can safely change a shared library and every consumer together, verified in one CI run) and unified tooling/dependency versions. A polyrepo naturally isolates each service's pipeline (simpler mental model, smaller blast radius per repo, independent versioning/release cadence per team) but makes genuinely cross-cutting changes (a shared library bump needed by 20 services) much harder to coordinate and verify atomically — often requiring a slower, sequenced multi-repo rollout with compatibility windows. Neither is universally "correct" — the choice trades coordination overhead against blast-radius isolation, and the CI/CD tooling investment required scales with how large and interdependent the codebase actually is.

### 30. What metrics would you track to know whether your CI/CD pipeline and deployment process are actually effective, and how do you use them?
The DORA four keys are the industry-standard framework: **deployment frequency** (how often you successfully release to production), **lead time for changes** (commit to production), **change failure rate** (% of deployments causing a production incident/rollback), and **mean time to recovery/restore (MTTR)** (how fast you recover from a failure). Track these longitudinally, not as one-off snapshots, and use them to diagnose *where* to invest — e.g., low deployment frequency with low change-failure-rate suggests overly conservative/manual gates worth automating further, while high deployment frequency with high change-failure-rate suggests the pipeline's testing/quality gates need strengthening before shipping faster, not after. Pair these with pipeline-specific operational metrics (pipeline duration, flaky-test rate, queue/wait time for runners) since a great DORA score can still mask a painfully slow or unreliable day-to-day developer pipeline experience underneath it.
