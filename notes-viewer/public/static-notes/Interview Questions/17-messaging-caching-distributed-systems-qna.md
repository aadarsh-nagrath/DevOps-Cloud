## Junior Level (0–2 yrs)

### 1. What is a message queue, and what problem does it solve?
A message queue lets one part of a system (a producer) send messages that another part (a consumer) processes independently, asynchronously, and at its own pace — decoupling the two so the producer doesn't need the consumer to be available or fast right at that moment. This solves problems like handling traffic spikes (queue absorbs a burst, workers drain it steadily rather than the burst directly overwhelming downstream processing), and letting producer and consumer scale, fail, and deploy independently of each other rather than being tightly coupled in a single synchronous request path.

### 2. What's the difference between synchronous (direct API call) and asynchronous (message queue) communication between two services?
A synchronous call blocks the caller until the callee responds — simple to reason about, but couples the caller's availability/latency directly to the callee's (if the callee is slow or down, the caller is too). An asynchronous, queue-based approach lets the caller hand off a message and continue immediately, with the actual processing happening independently, later — trading immediate consistency/simplicity for resilience to the consumer being temporarily slow/unavailable, at the cost of added complexity (the caller no longer gets an immediate result, and needs a way to be informed of completion/failure if it cares about the outcome).

### 3. What is Kafka, at a basic level?
Apache Kafka is a distributed event-streaming platform — producers publish messages ("events") to named **topics**, which are durably stored and can be independently consumed by multiple consumers/consumer groups, each tracking its own read position ("offset") in the topic. Unlike a traditional queue where a message is typically removed once consumed, Kafka retains messages for a configured retention period regardless of whether they've been consumed, allowing multiple independent consumers to read the same data, and even allowing a consumer to "replay" from an earlier offset.

### 4. What is RabbitMQ, and how does it conceptually differ from Kafka?
RabbitMQ is a traditional message broker implementing flexible routing patterns (direct, topic, fanout exchanges) to deliver messages to one or more queues, with messages typically removed once successfully consumed/acknowledged. Conceptually, RabbitMQ is oriented around message *delivery* to consumers with rich routing logic (good fit for task queues, request routing, complex routing rules), while Kafka is oriented around durable, replayable *event log* storage at very high throughput (good fit for event streaming, analytics pipelines, and cases where multiple independent systems need to consume the same stream of events, potentially at different times).

### 5. What is caching, and why does adding a cache improve performance?
Caching stores a copy of frequently-accessed or expensive-to-compute data somewhere faster to retrieve than its original source, so subsequent requests for the same data can be served from the cache instead of repeating the expensive original operation (a slow database query, a costly computation, a remote API call). It improves performance both by reducing latency (a cache is generally faster to read from) and by reducing load on the original source (fewer requests actually reach the database/API).

### 6. What is Redis, and what are the most common things it's used for?
Redis is an in-memory data store supporting rich data structures (strings, hashes, lists, sets, sorted sets) with very low latency, since data lives in RAM rather than on disk. Common uses: caching (storing frequently-read data to reduce database load), session storage (externalizing web application session state so any backend instance can serve any user, supporting stateless horizontal scaling), rate limiting, and as a lightweight message broker/pub-sub system for simpler use cases than a dedicated queue like Kafka/RabbitMQ warrants.

### 7. What's the difference between a CDN and an application-level cache (like Redis)?
A **CDN** (Content Delivery Network) caches content (images, static assets, sometimes API responses) at edge locations *geographically close to end users*, reducing latency by serving from a nearby location instead of your origin server, and reducing load on your origin entirely for cached content. An **application-level cache** (Redis, Memcached) sits close to your *application/database*, reducing the cost/latency of repeated backend operations (database queries) — the two operate at different layers and are commonly used together (a CDN in front of everything for static/cacheable content, an application cache behind it for dynamic data).

### 8. What is database replication, at a basic level?
Replication maintains copies of a database's data across multiple servers, so a **primary/leader** handles writes and one or more **replicas/followers** receive a continuous copy of those changes. This provides read scalability (routing read queries to replicas to spread load) and availability (a replica can be promoted to primary if the original primary fails), at the cost of replicas typically lagging slightly behind the primary (replication lag) unless synchronous replication is used, which trades that lag for added write latency.

### 9. What is database sharding, at a basic level?
Sharding splits a single logical database's data horizontally across multiple separate database instances (shards), each holding a subset of the total data (e.g. partitioned by customer ID range or a hash of a key) — used when a dataset/write-throughput requirement grows beyond what a single database instance can handle even with read replicas (which only help read scaling, not write scaling, since all writes still go to one primary). It adds real complexity — queries spanning multiple shards, rebalancing data if shard boundaries need to change, and maintaining referential integrity across shards — which is why it's generally adopted only once genuinely necessary, not by default.

### 10. What's the difference between a monolithic application and a microservices architecture?
A monolith is a single, unified application/codebase handling all functionality, typically deployed as one unit. Microservices split functionality into multiple independently deployable services, each typically owning its own data and communicating over the network (APIs, message queues). Microservices offer independent scaling/deployment/technology choice per service at the cost of significantly more operational complexity (network calls where there used to be in-process function calls, distributed transactions/consistency challenges, more moving parts to deploy/monitor) — a tradeoff that's genuinely beneficial at a certain scale/team-size and genuinely premature/costly below it.

## Mid Level (2–5 yrs)

### 11. Explain the CAP theorem, and why a distributed system can't have all three of Consistency, Availability, and Partition tolerance simultaneously.
CAP theorem states that in the presence of a **network partition** (P — some nodes can't communicate with others, which is unavoidable in any real distributed system given real networks eventually fail), a system must choose between **Consistency** (every read reflects the most recent write, seen identically everywhere) and **Availability** (every request gets a response, even if it might not reflect the latest write) — you cannot guarantee both simultaneously during a partition, because satisfying consistency requires refusing to answer (or waiting) on the side of the partition that can't confirm it has the latest data, which directly sacrifices availability, and vice versa. Since partitions are a "when," not "if," in real distributed systems, CAP is really a statement about which of Consistency or Availability a system prioritizes *during* a partition, not a permanent, static three-way tradeoff a system makes once — many systems tune this behavior per-operation (e.g. DynamoDB and Cassandra offer configurable consistency levels per read/write).

### 12. What's the practical difference between strong consistency and eventual consistency, and how do you decide which a given use case actually needs?
Strong consistency guarantees any read immediately reflects the most recent completed write, everywhere — simpler to reason about, but generally requires more coordination (higher latency, reduced availability during partitions/failures). Eventual consistency guarantees that, absent new writes, all replicas *will eventually* converge to the same value, but a read shortly after a write might briefly return stale data. The decision should be use-case-driven: a bank account balance or an inventory count for the last item in stock generally demands strong consistency (showing stale data risks real, visible incorrect behavior — overselling, incorrect balance); a social media "like count" or a view counter is a textbook fit for eventual consistency, since a few seconds of staleness has no meaningful real-world consequence and the massive availability/performance benefit is a clear win — the mistake to avoid is defaulting to one model universally rather than actually reasoning per use case about what staleness would actually cost.

### 13. Explain the difference between "at-most-once," "at-least-once," and "exactly-once" message delivery guarantees, and which is actually achievable in practice.
**At-most-once**: a message might be lost but is never redelivered/duplicated (fire-and-forget, no retry). **At-least-once**: a message is guaranteed to be delivered, but might be delivered more than once (a consumer processes it, but the acknowledgment back to the broker is lost, so the broker redelivers it) — the most common practical guarantee, since it just requires retry-until-acknowledged logic. **Exactly-once** — delivered precisely once, no loss and no duplication — is genuinely very hard to achieve end-to-end in a truly distributed system with independent failure modes (it's more accurate to describe most "exactly-once" systems as achieving effectively-exactly-once *processing* through at-least-once delivery combined with **idempotent** consumer-side processing — the consumer can safely handle a duplicate delivery without a duplicated effect, e.g. using each message's unique ID to detect and ignore already-processed duplicates — rather than claiming true delivery-layer exactly-once semantics).

### 14. What is a dead-letter queue (DLQ), and why is it an essential part of a production message-processing architecture, not an optional nice-to-have?
A dead-letter queue captures messages that repeatedly fail processing (after a defined retry limit) instead of either endlessly retrying them (blocking the queue/consumer on one poison message) or silently dropping them (losing them with no visibility at all). Without a DLQ, a single malformed or unexpectedly-problematic message can either cause an infinite retry loop that stalls processing of every message behind it in the queue, or simply vanish without anyone noticing — a DLQ, combined with actual monitoring/alerting on messages landing in it, is what turns "a message failed processing" from a silent data-loss/stuck-pipeline risk into a visible, investigable, and recoverable (messages can typically be inspected and manually replayed once the underlying issue is fixed) operational event.

### 15. How would you decide between using a message queue (RabbitMQ/SQS) versus an event streaming platform (Kafka) for a given integration?
Reach for a traditional queue (RabbitMQ, SQS) when the pattern is genuinely "distribute discrete tasks to be processed, typically once, by one of several workers" (a task queue, a job processing pipeline) — simpler operationally, and message removal after successful processing matches the "each task done once" semantics naturally. Reach for Kafka (or a similar event-streaming platform) when you need very high sustained throughput, multiple independent consumers/systems needing to read the *same* stream of events (potentially at different times, or replaying historical events), or when the data itself is naturally an ordered log of events that has value beyond just "get this task done once" (event sourcing, analytics pipelines, feeding multiple downstream systems from one shared event stream) — Kafka's operational complexity (partition management, consumer group rebalancing, more involved cluster operations) is a real cost that should be justified by actually needing those capabilities, not adopted by default because it's the more prominent/popular technology.

### 16. What's the difference between a "cache-aside," "write-through," and "write-behind" caching strategy?
**Cache-aside** (the most common pattern): the application checks the cache first; on a miss, it reads from the source of truth (database) and populates the cache for next time — the cache is populated lazily, only for data actually requested. **Write-through**: writes go to the cache and the underlying data store synchronously together, keeping the cache always current for written data, at the cost of added write latency. **Write-behind** (write-back): writes go to the cache immediately and are asynchronously flushed to the underlying store later — fastest writes, but with a real risk of data loss if the cache fails before the asynchronous flush completes, so it's only appropriate when that risk is acceptable for the specific data involved.

### 17. What is cache invalidation, and why is it famously described as "one of the two hard problems in computer science"?
Cache invalidation is the problem of ensuring cached data is removed/updated when the underlying source data changes, so the cache doesn't keep serving stale data indefinitely. It's genuinely hard because there's no universally correct strategy — a short TTL (time-to-live) risks unnecessary cache misses/load even when data hasn't actually changed, while a long TTL risks serving meaningfully stale data for longer; explicit invalidation (actively clearing/updating a cache entry the moment its source data changes) is more precise but requires reliably identifying and triggering invalidation for every code path that could change that data, which is easy to miss in a complex system with multiple ways data gets updated — the "famous hard problem" framing (alongside naming things, and off-by-one errors, in the well-known programmer joke) reflects that there's no simple, universally-correct answer, only tradeoffs suited to specific data's actual staleness tolerance.

### 18. What is an API Gateway, and what functionality does it typically centralize for a microservices architecture?
An API Gateway sits in front of a collection of backend microservices, providing a single entry point for external clients rather than exposing every service directly. It typically centralizes cross-cutting concerns that would otherwise need to be reimplemented in every individual service: authentication/authorization, rate limiting, request routing (mapping external routes to the right internal service), request/response transformation, and often aggregating multiple backend calls into a single client-facing response — letting individual microservices focus on their own business logic rather than each reimplementing these shared concerns independently.

## Senior Level (5+ yrs)

### 19. Design a message-processing architecture for an order-processing system that must never lose an order, must handle downstream service outages gracefully, and must avoid double-charging customers on retries. Walk through the key decisions.
Use a durable message queue/log (Kafka, or SQS with appropriate durability configuration) as the entry point for order events, since it decouples order intake from downstream processing and durably persists the order the moment it's accepted, before any downstream processing has even started — this alone prevents the class of failure where an order is "lost" because a downstream service happened to be down at the exact moment it arrived. Design every downstream consumer to be **idempotent** with respect to a stable order ID (checking "have I already processed this exact order" before acting, using the order ID as a deduplication key) — this is what specifically prevents double-charging on retries, since at-least-once delivery semantics (the realistic, achievable guarantee, per the earlier question) mean some retried/duplicate delivery is expected and must be safely absorbed by the consumer rather than assumed away. Use a dead-letter queue with alerting for orders that fail processing repeatedly, so a persistently failing order becomes a visible, investigable event rather than either blocking the whole pipeline or silently vanishing. For graceful handling of a downstream outage specifically (say, the payment processor is down), the queue's natural buffering already provides significant resilience (orders simply queue up and are processed once the dependency recovers) — combined with a circuit breaker on the payment-processor call to avoid a pile of workers all repeatedly hammering an already-down dependency, and clear customer-facing status communication (an order confirmation acknowledging receipt, distinct from confirming actual payment completion) so the customer experience degrades gracefully rather than customers repeatedly retrying and compounding the load during the outage.

### 20. How would you reason about and design for the tradeoffs of introducing a cache into a system where staleness genuinely matters (e.g. inventory counts for a limited-stock item during a flash sale)?
This is a case where the earlier "eventual consistency is often fine" framing explicitly does *not* apply — serving a stale "in stock" count during a high-contention flash sale directly causes overselling, a real, customer-facing, and often costly failure mode. The design should reason explicitly about *which specific operations* actually need strong consistency (the final decrement/reservation of the last few units of genuinely scarce inventory) versus which can tolerate a cache (the general product page's displayed stock count for an item with abundant inventory, where staleness has no real consequence) — rather than applying one uniform caching policy to "inventory" as an undifferentiated whole. For the genuinely contention-sensitive operation, the correct design usually routes around the cache entirely for the actual reservation/decrement (a strongly consistent, atomic operation directly against the source of truth, or a dedicated high-throughput coordination mechanism specifically built for exactly this kind of contended counter) while still using aggressive caching for the surrounding, non-contended parts of the experience (product details, images, general availability messaging) — the skill being tested here is recognizing that "should we cache this" is a question that needs to be asked per-operation based on actual consistency requirements, not answered once for an entire feature area.

### 21. Your organization is considering migrating from a monolith to microservices primarily because "the monolith is slow to deploy and everyone's stepping on each other." What questions would you ask before recommending that path, and what alternatives might address the same pain without the full cost of microservices?
Before recommending a full microservices migration (which carries substantial, real operational cost — distributed transactions, network reliability between what used to be in-process calls, many more independently-deployed and independently-monitored units, and usually more infrastructure/platform investment to do well), probe whether the actual root cause is architectural coupling or simply *organizational/process* friction that a less drastic change could address: is the slow-deploy pain caused by genuine tight coupling in the codebase (a change to one area unavoidably requires touching/retesting unrelated areas), or by process issues that a monolith doesn't inherently cause (a single, slow, manual test suite gating every deploy; a single team owning deploys for a codebase multiple independent teams contribute to, creating a bottleneck; poor internal module boundaries within the monolith causing unrelated changes to conflict, which better internal modularity — a "modular monolith" — could address without actually splitting into separately-deployed services at all). Alternatives worth genuinely considering first: improving internal modularity/ownership boundaries within the existing monolith (often addresses "everyone's stepping on each other" directly, since the real cause is frequently unclear internal boundaries, not the deployment unit itself), investing in CI/CD/test suite speed and reliability (directly addresses "slow to deploy" without any architectural change), and, if genuinely warranted, extracting only the *specific* highest-pain, most independently-scalable pieces into separate services incrementally (a strangler-fig-style migration) rather than committing to a full, upfront microservices rewrite — the senior-level judgment being demonstrated here is recognizing that microservices is a tool suited to specific, real problems (independent scaling needs, genuinely independent team ownership at scale) and not treating it as a default fix for what might actually be a process or code-organization problem addressable far more cheaply.
