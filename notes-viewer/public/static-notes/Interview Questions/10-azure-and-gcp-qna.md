## Junior Level (0–2 yrs)

### 1. What is Azure, and how are Azure "Resource Groups" different from AWS's account/VPC model?
Azure is Microsoft's cloud platform. A **Resource Group** is a logical container grouping related resources (VMs, databases, networking) that share the same lifecycle, deployed and managed/deleted together — there's no direct AWS equivalent as a single primitive (AWS's closest analogues are spread across accounts, tags, and CloudFormation stacks). Every Azure resource must belong to exactly one resource group, which becomes a natural unit for access control (RBAC scoping), cost tracking, and bulk cleanup (deleting a resource group deletes everything in it).

### 2. What is Azure Active Directory / Microsoft Entra ID, and how does it relate to AWS IAM?
Microsoft Entra ID (formerly Azure Active Directory / Azure AD) is Microsoft's identity platform — it's both the identity backbone for Microsoft 365/enterprise identity *and* the identity provider for Azure resource access control (via Azure RBAC). This is a meaningfully different model from AWS IAM: Entra ID identities are the same identities used for organizational single sign-on broadly, not a cloud-resource-scoped identity system built independently of your company's directory — a common real-world consequence is that Azure RBAC and organizational identity/access governance are much more tightly coupled than the equivalent in AWS.

### 3. What is an Azure Virtual Machine, and what's the equivalent of an AWS Auto Scaling Group?
An Azure VM is the direct equivalent of an EC2 instance. The equivalent of an ASG is a **Virtual Machine Scale Set (VMSS)** — a group of identical, load-balanced VMs that can automatically scale in/out based on metrics or a schedule, analogous in purpose to EC2 Auto Scaling Groups.

### 4. What is Azure Blob Storage, and how does it compare to AWS S3?
Blob Storage is Azure's object storage service, directly analogous to S3 — storing unstructured data (blobs) in containers (S3's "buckets"), with access tiers (Hot, Cool, Archive) analogous to S3's Standard/Infrequent-Access/Glacier tiers, trading storage cost against retrieval cost/latency the same way.

### 5. What is AKS, and what's the core conceptual similarity to EKS?
AKS (Azure Kubernetes Service) is Azure's managed Kubernetes offering — Azure manages and operates the control plane (and, notably, does so at no extra charge for the control plane itself on the free tier, unlike EKS's per-cluster control plane fee) while you manage node pools. Conceptually it's the same managed-Kubernetes model as EKS/GKE: you get a conformant, standard Kubernetes API, with the cloud-specific differences mostly in how networking (Azure CNI vs. kubenet), identity (Azure AD Workload Identity, analogous to IAM Roles for Service Accounts on EKS), and storage integrate with the rest of that specific cloud's ecosystem.

### 6. What is Azure DevOps, and how does it relate to GitHub Actions?
Azure DevOps is Microsoft's integrated suite covering source repos (Azure Repos), CI/CD pipelines (Azure Pipelines), work tracking (Boards), package feeds (Artifacts), and test management — historically Microsoft's primary DevOps toolchain, distinct from GitHub Actions (which Microsoft also owns, via GitHub, and has increasingly unified investment toward). Azure Pipelines' YAML pipeline syntax is conceptually similar to GitHub Actions/GitLab CI (stages, jobs, steps, YAML-defined) but with its own specific syntax and marketplace of tasks rather than "actions."

### 7. What is Google Cloud Platform (GCP), and what's the basic organizing hierarchy of resources?
GCP is Google's cloud platform. Its resource hierarchy is **Organization → Folders → Projects → Resources** — a **Project** is the fundamental unit almost everything belongs to (billing, APIs enabled, IAM policies are commonly scoped here), somewhat analogous to (but more granular/lightweight than) an AWS account — many teams create many GCP projects (dev, staging, per-team, per-application) far more liberally than most organizations create separate AWS accounts.

### 8. What is GKE, and what is "Autopilot mode"?
GKE (Google Kubernetes Engine) is Google's managed Kubernetes service — widely regarded as one of the most mature managed Kubernetes offerings, since Google originated Kubernetes itself. **Autopilot mode** goes further than standard managed node pools — Google manages the underlying nodes entirely (you don't choose instance types or manage node pools at all), billing per-Pod-resource-request rather than per-node, trading some low-level infrastructure control for significantly reduced operational overhead — the standard "Standard mode" GKE still gives you full node pool control, similar to EKS/AKS.

### 9. What is Google Cloud Storage (GCS), and BigQuery, at a basic level?
GCS is GCP's object storage service (S3/Blob Storage equivalent), with storage classes (Standard, Nearline, Coldline, Archive) again trading cost against access frequency. **BigQuery** is GCP's serverless, fully-managed data warehouse for large-scale analytics via SQL — you don't provision or manage any infrastructure; you load or stream data in and run (potentially massive-scale) SQL queries against it, paying primarily for storage and the data volume actually scanned per query.

### 10. What is Cloud Run, and how does it compare to AWS Lambda / Fargate?
Cloud Run runs stateless containers on a fully-managed, serverless platform, scaling automatically (including to zero) based on incoming request traffic, billed only for actual usage. Unlike Lambda (which runs a specific function-handler model with language-specific runtimes), Cloud Run runs *any* container image exposing an HTTP port — closer conceptually to a serverless version of Fargate (run any container, no server management) than to Lambda's function-centric model, making it a popular choice for teams wanting serverless simplicity without restructuring an existing containerized application into discrete functions.

## Mid Level (2–5 yrs)

### 11. Explain Azure RBAC's scope hierarchy (Management Group → Subscription → Resource Group → Resource), and how permission inheritance works.
Azure RBAC role assignments can be made at any level of this hierarchy, and inherit downward — a role assigned at the Subscription level applies to every Resource Group and resource within it, unless a more specific (and typically more restrictive, though it can also grant additional access) assignment exists lower down. **Management Groups** sit above subscriptions, letting an organization apply policy/RBAC consistently across many subscriptions at once (analogous in spirit to AWS Organizations + SCPs, though the mechanics differ) — the practical implication for a senior engineer is that "why does this identity have access to this resource" often requires checking every level of this hierarchy, not just the resource's own explicit role assignments, since an inherited assignment several levels up is easy to overlook.

### 12. What is an Azure Service Principal, and how is it different from a Managed Identity?
A **Service Principal** is an application identity with credentials (a secret or certificate) you must generate, store, and rotate yourself — used historically for any automation/application needing to authenticate to Azure APIs, but carrying the same long-lived-credential-management burden as an AWS IAM access key. A **Managed Identity** is Azure's answer to that problem (analogous to an AWS IAM role attached to an EC2 instance/Lambda) — Azure automatically manages the underlying credential entirely, with no secret for you to store/rotate at all, assigned directly to a resource (a VM, an App Service, an AKS pod via Workload Identity) — the modern recommended default over Service Principals with manually-managed secrets wherever the workload runs on Azure infrastructure that supports it.

### 13. What is Azure Policy, and how does it relate to (and differ from) Azure RBAC?
RBAC controls *who can do what* (authorization). **Azure Policy** controls *what configurations are allowed to exist*, regardless of who's making the change — e.g. "deny creation of any storage account without encryption enabled" or "require a specific tag on every resource," enforced even against an identity that RBAC would otherwise permit to create that resource. This is the same conceptual role Service Control Policies play in AWS Organizations or Organization Policies play in GCP — a guardrail layer independent of, and evaluated alongside, identity-based permissions.

### 14. What's the difference between GCP's IAM "basic roles," "predefined roles," and "custom roles"?
**Basic roles** (Owner, Editor, Viewer) are broad, legacy, project-wide roles generally discouraged for anything beyond the smallest projects, since they grant sweeping permissions across nearly every GCP service at once. **Predefined roles** are Google-curated, service-specific roles scoped to a reasonable set of related permissions (e.g. `roles/compute.instanceAdmin`) — the recommended default for most use cases. **Custom roles** let you assemble an exact, minimal set of individual permissions tailored to a specific need when no predefined role fits precisely — following least privilege more closely than either basic or predefined roles, at the cost of more roles to define and maintain over time.

### 15. Explain GCP's Shared VPC and Azure's Virtual Network Peering — why would a multi-team organization use either?
**Shared VPC** (GCP) lets one "host" project own the actual VPC network, while other "service" projects attach to and provision resources within it — centralizing network administration/security while still letting individual teams manage their own project's resources/billing independently, avoiding the connectivity complexity of many separately-networked projects needing to be peered together. **Azure VNet Peering** connects two independent virtual networks (potentially in different subscriptions) so resources in each can communicate as if on the same network — conceptually similar to AWS VPC Peering, used when networks genuinely need to stay administratively separate but still communicate, rather than sharing one network's administration entirely as Shared VPC does.

### 16. What's the equivalent of AWS's S3 + CloudFront (static hosting + CDN) pattern on Azure and GCP?
On Azure: Blob Storage (static website hosting enabled) fronted by **Azure CDN** (or Azure Front Door for more advanced routing/WAF capability). On GCP: Cloud Storage (static website hosting) fronted by **Cloud CDN**, typically behind a Google Cloud Load Balancer. The underlying pattern is identical across all three clouds — durable, cheap object storage for the actual static assets, with a CDN layer caching content at edge locations close to users to reduce latency and origin load.

### 17. How does GCP's global load balancing differ conceptually from AWS/Azure's more region-scoped load balancers?
GCP's HTTP(S) Load Balancer is a genuinely **global**, anycast-based service — a single global IP address in front of backends across multiple regions, with Google's network routing users to the nearest healthy region automatically, without needing separate regional load balancers plus DNS-based (Route 53 latency routing) global traffic steering layered on top, as is typically needed to achieve similar behavior on AWS. This reflects GCP's approach of building more directly on Google's own global network backbone, whereas AWS/Azure's global traffic distribution more commonly composes a DNS layer (Route 53 / Azure Traffic Manager) on top of otherwise region-scoped load balancers.

### 18. What's the equivalent of AWS CloudWatch on Azure and GCP?
Azure: **Azure Monitor** (metrics, Log Analytics for logs/queries via Kusto Query Language (KQL), Application Insights for application-level APM). GCP: **Cloud Monitoring** (formerly Stackdriver, metrics/dashboards/alerting) paired with **Cloud Logging** (formerly Stackdriver Logging) for centralized log aggregation and querying. All three follow the same underlying pattern — metrics, logs, and alerting as separate but integrated pillars — with the main practical differences being query language (KQL vs. CloudWatch Logs Insights vs. Cloud Logging's query language) and how deeply each integrates with that specific cloud's other services.

## Senior Level (5+ yrs)

### 19. You're designing a genuinely multi-cloud architecture (not just "we use two clouds for different unrelated things," but workloads that need to run consistently across both). What are the real technical challenges, and where does abstraction actually help vs. hurt?
Genuine multi-cloud portability is hardest exactly where each cloud differentiates most: managed database services, IAM/identity models, native serverless offerings, and networking primitives (VPC peering/Transit Gateway vs. VNet peering vs. Shared VPC are conceptually similar but not API-compatible) all differ enough that "write once, run identically anywhere" is largely aspirational for anything beyond stateless compute on Kubernetes. Abstraction layers (Terraform as a single IaC tool, Kubernetes as a common compute/orchestration layer, Crossplane for cloud-resource abstraction) genuinely help for the *compute and orchestration* layer, letting the same container/Kubernetes-based workload run on EKS/AKS/GKE with only modest cloud-specific configuration differences. Abstraction hurts when it pushes teams toward the lowest-common-denominator subset of each cloud's *capabilities* to preserve portability — deliberately avoiding a cloud's genuinely superior native managed service (a fully-managed database, a serverless offering with better cold-start characteristics) purely for theoretical multi-cloud portability that may never actually be exercised is a common, costly overcorrection; the honest senior-level framing is that multi-cloud is usually adopted for specific, concrete reasons (a specific customer/compliance requirement, avoiding single-vendor negotiating leverage, disaster-recovery independence from one provider's global outage) and the architecture should be scoped to actually serve *that* concrete reason, not a vague, unbounded "avoid all lock-in everywhere" goal that trades away real capability for portability nobody ends up using.

### 20. How would you approach cost governance across Azure and GCP (or a multi-cloud environment), given each cloud's billing/tagging model differs?
Establish a consistent tagging/labeling taxonomy (cost center, environment, team, application) enforced at resource-creation time (Azure Policy / GCP Organization Policy, or an admission-control equivalent) *before* trying to build any cross-cloud cost reporting, since inconsistent or missing tags/labels are the actual root cause of most failed cost-attribution efforts, not a lack of reporting tooling. Aggregate billing data from each cloud's native export (Azure Cost Management exports, GCP Billing export to BigQuery) into a common data warehouse or a dedicated FinOps/cloud-cost-management platform, normalizing each cloud's different service-naming and pricing-dimension conventions into a common schema so cross-cloud comparisons and total-cost-of-ownership reporting are actually meaningful rather than three separate, incompatible reports. Establish the same proactive-budget-alerting and anomaly-detection discipline per cloud (Azure Budgets, GCP Budgets & Alerts) rather than relying on a slower, centralized monthly reconciliation process to catch runaway costs — the earlier-cited "prevent, don't just detect after the bill arrives" principle applies identically regardless of which cloud(s) are involved.

### 21. Compare the identity/authentication model differences between AWS IAM, Azure RBAC/Entra ID, and GCP IAM — what's a real operational trap for someone experienced in one cloud moving to another?
AWS IAM is largely self-contained to AWS itself (an IAM user/role isn't inherently tied to your company's broader corporate identity system, though it's commonly federated via SSO). Azure RBAC is built directly atop Entra ID, your organization's actual enterprise identity system used for Microsoft 365/SSO broadly — meaning Azure resource access decisions are far more entangled with your company's overall identity/group structure than the AWS equivalent, for better (single source of truth) and worse (a change to an organizational security group made for unrelated reasons can silently affect Azure resource access). GCP IAM sits closer to AWS's model conceptually (project-scoped permissions, service accounts analogous to IAM roles) but with its distinctively liberal multi-project resource hierarchy — a common real trap for an AWS-experienced engineer moving to GCP is under-appreciating how routinely GCP organizations create new projects (as the primary isolation/billing boundary, more like spinning up a new AWS sub-account than creating a new AWS resource group) versus an AWS-native instinct to keep everything in fewer accounts, and for an engineer moving into Azure specifically, the trap is treating Azure RBAC as if it were as cleanly separable from broader organizational identity governance as AWS IAM typically is — it usually isn't, and treating it that way leads to access-review and least-privilege efforts that miss how much real access flows through inherited group membership rather than explicit Azure role assignments.
