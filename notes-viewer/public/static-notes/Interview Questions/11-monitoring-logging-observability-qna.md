## Junior Level (0–2 yrs)

### 1. What's the difference between monitoring and observability?
Monitoring is watching a predefined set of known metrics/dashboards/alerts to answer questions you already knew to ask ("is CPU high," "is the error rate above threshold"). Observability is the broader capability to answer *new, previously unanticipated* questions about a system's internal state from its external outputs — being able to explore "why is this specific request slow" for a problem you never explicitly instrumented a dashboard for. Monitoring is necessary but not sufficient; observability is what lets you actually debug novel, complex production issues rather than only detecting known failure modes.

### 2. What are the "three pillars of observability" — metrics, logs, and traces?
**Metrics** are numeric measurements aggregated over time (request rate, error count, CPU usage) — cheap to store and query, great for trends/alerting, but lose individual-event detail. **Logs** are discrete, timestamped event records (often with rich context) — detailed but more expensive to store/query at volume. **Traces** follow a single request's journey across multiple services in a distributed system, showing where time was spent at each hop — essential for diagnosing latency in microservice architectures where a single user request touches many services. Each answers a different kind of question, and mature observability uses all three together, correlated (e.g. jumping from a metric spike to the relevant logs/traces for that time window).

### 3. What is Prometheus, and how does its "pull" model differ from a "push" model?
Prometheus is an open-source metrics collection and time-series database. It uses a **pull** model — Prometheus itself periodically scrapes (`HTTP GET /metrics`) each target it's configured to monitor, rather than targets pushing metrics to it. This makes Prometheus's own health directly informative (a target that stops responding to scrapes is immediately visibly "down" to Prometheus) and avoids needing every monitored service to know about and reliably push to a central collector — though it requires Prometheus to be able to reach every target's network location, which is why short-lived/batch jobs that don't live long enough to be scraped use the separate **Pushgateway** component to push their results instead.

### 4. What is a Prometheus exporter?
An exporter is a small process that exposes metrics about a system in Prometheus's text-based format, translating that system's native metrics into something Prometheus can scrape — used for systems that don't natively expose Prometheus-format metrics (`node_exporter` for host-level OS metrics, `mysqld_exporter` for MySQL, `blackbox_exporter` for probing endpoints externally).

### 5. What is Grafana, and how does it relate to Prometheus?
Grafana is a visualization/dashboarding tool — it doesn't collect or store metrics itself, but queries data sources (Prometheus being the most common, but also Loki, Elasticsearch, CloudWatch, and many others) and renders that data as dashboards, graphs, and alerts. Prometheus and Grafana are commonly paired (Prometheus for collection/storage/querying via PromQL, Grafana for visualization) but each can be used with other tools too — they're not tightly coupled to each other specifically.

### 6. What is the ELK stack, and what does each letter stand for?
**Elasticsearch** (a distributed search/analytics engine used as the storage/query backend for logs), **Logstash** (a log ingestion/processing pipeline that parses, transforms, and forwards log data), and **Kibana** (the visualization/dashboarding UI for exploring data in Elasticsearch) — together forming a common centralized logging stack. **Filebeat** (a lightweight log-shipping agent) is often added alongside Logstash (forming "ELK + Beats," sometimes called the "Elastic Stack"), and Fluentd/Fluent Bit are common Logstash alternatives, particularly in Kubernetes environments ("EFK" stack).

### 7. Why centralize logs instead of just SSH-ing into each server and reading local log files?
At any meaningful scale (more than a handful of servers, or any containerized/auto-scaled environment where individual hosts/containers are ephemeral) SSH-ing into individual machines doesn't scale operationally, and container/instance churn means a crashed container's logs may be gone entirely once it's replaced. Centralized logging aggregates logs from every host/container into one searchable system, letting you correlate events across services in one place, retain logs longer than any single ephemeral host's disk would allow, and search across the whole fleet with one query instead of dozens of manual SSH sessions.

### 8. What is an alert, and what's the difference between an alert and a dashboard?
A dashboard is something a human actively looks at to understand system state — useful, but only informative if someone is actually watching it at the right moment. An **alert** is a rule that actively notifies someone (page, Slack message, email) when a defined condition is met, without requiring anyone to be watching a dashboard at that exact moment — the mechanism that actually gets a human's attention when something goes wrong, versus a dashboard that could show a problem for hours before anyone happens to look at it.

### 9. What is log level (DEBUG, INFO, WARN, ERROR), and why does it matter for both cost and signal?
Log levels categorize the severity/verbosity of a log message. Setting the wrong level in production has real costs both ways: leaving verbose `DEBUG` logging on in production generates enormous log volume (increasing storage/ingestion cost and making it harder to find the signal you actually need amid the noise), while under-logging (only `ERROR`) can leave you with no context at all when investigating an incident, since the useful diagnostic detail was never captured in the first place — most teams run at `INFO` level in production by default, with the ability to temporarily/dynamically raise verbosity for specific components during an active investigation.

### 10. What's the difference between structured logging (JSON logs) and plain-text logs?
Plain-text logs are free-form human-readable strings ("User 123 logged in at 10:32am") that require regex/pattern-matching to extract structured data programmatically. Structured logs (`{"event": "login", "user_id": 123, "timestamp": "..."}`, typically JSON) encode fields explicitly, letting log aggregation systems (Elasticsearch, Loki) index and query specific fields directly and reliably (`user_id: 123`) without fragile parsing — the standard recommended practice for any log a system might need to query/alert on programmatically, rather than only read by a human eyeball.

## Mid Level (2–5 yrs)

### 11. Explain PromQL basics — what does a query like `rate(http_requests_total[5m])` actually compute?
`http_requests_total` is a Prometheus **counter** metric (monotonically increasing, e.g. total requests served since the process started). `rate(...[5m])` computes the *per-second average rate of increase* of that counter over the trailing 5-minute window, correctly handling counter resets (e.g. after a process restart, where the raw counter value drops back to zero) — this is why you virtually always wrap a counter in `rate()` before using it in an alert or graph, rather than graphing the raw ever-increasing counter value directly, which would be far less useful for understanding current traffic rate.

### 12. What's the difference between a Prometheus counter, gauge, histogram, and summary metric type?
A **counter** only increases (or resets to zero on restart) — total requests, total errors. A **gauge** can go up or down — current memory usage, current number of active connections. A **histogram** samples observations (like request durations) into configurable buckets, letting you compute approximate quantiles/percentiles server-side at query time and aggregate/sum across instances (since raw bucket counts are simple counters underneath). A **summary** also captures observations and can expose pre-calculated quantiles, but those quantiles are calculated client-side at the individual instance and generally *cannot* be meaningfully aggregated/averaged across multiple instances — for this reason, histograms are generally the preferred choice for latency measurements across a fleet of replicas, despite requiring you to choose bucket boundaries in advance.

### 13. What is cardinality in the context of metrics, and why is "high cardinality" a real operational problem, not just a performance nitpick?
Cardinality is the number of unique label-value combinations a metric can produce — a metric labeled by `user_id` or a raw, unbounded URL path can explode into millions of distinct time series, since every unique label combination becomes its own separately-stored series. High cardinality directly degrades Prometheus's (and most time-series databases') memory usage, query performance, and storage cost, and in severe cases can effectively take down the monitoring system itself — a classic real-world incident is an engineer adding a well-intentioned but unbounded label (a full request path, a customer ID) to a metric, causing memory usage on the Prometheus server to spike and query latency to degrade cluster-wide, well after the change seemed to work fine in initial testing at low traffic.

### 14. What are SLIs, SLOs, and SLAs, and how do they relate to each other?
An **SLI** (Service Level Indicator) is an actual, measured metric of some aspect of service behavior (e.g. "percentage of requests served in under 200ms"). An **SLO** (Service Level Objective) is an internal target for that SLI (e.g. "99.9% of requests under 200ms, measured over a rolling 30 days") — the goal you actually operate against day to day. An **SLA** (Service Level Agreement) is an externally-facing, often contractual commitment (frequently with financial penalties for breach) typically set *looser* than your internal SLO, so you have margin to notice and respond to degradation before you actually breach a customer-facing contractual commitment.

### 15. What is an error budget, and how does it change the conversation between reliability and feature velocity?
An error budget is the inverse of your SLO — if your SLO is 99.9% availability, your error budget is the remaining 0.1% of allowed unreliability over that period. As long as you're within budget, the team has explicit, quantified room to take risks (ship faster, run planned maintenance, take on technical debt tradeoffs) — once the budget is exhausted, the agreed-upon response is to shift focus toward reliability work (freezing risky releases, prioritizing fixing root causes) until the budget recovers. This reframes reliability vs. feature velocity from a subjective, often political argument into a data-driven, pre-agreed policy — a core SRE practice popularized by Google's SRE book.

### 16. What is distributed tracing, and what problem does it solve that logs and metrics alone don't?
In a microservices architecture, a single user request might touch a dozen services — metrics tell you aggregate behavior ("p99 latency is high") and logs give you detail *per service*, but neither alone easily answers "for this one specific slow request, which of the 12 services it touched was actually the bottleneck, and in what order did the calls happen." Distributed tracing (OpenTelemetry, Jaeger, Zipkin) propagates a shared trace ID across every service a request touches, recording timed "spans" for each hop, letting you reconstruct the full request path and see exactly where time was spent — solving the specific problem of debugging latency/errors that only manifest from the interaction *between* services, not visible from any single service's own logs/metrics in isolation.

### 17. What is Loki, and how is its architecture/cost model different from Elasticsearch for log storage?
Loki (from Grafana Labs) is a log aggregation system deliberately designed to be much cheaper to operate than Elasticsearch for the common case, by taking a different indexing approach: rather than fully indexing the *content* of every log line (as Elasticsearch does, which is powerful but storage/compute-intensive), Loki indexes only a small set of labels (similar to Prometheus's label model) and stores the actual log content compressed, unindexed — queries filter first by labels (cheap) then grep through the matching compressed chunks (still fast enough for most real-world query patterns, given labels narrow the search space significantly first). This trades some full-text-search flexibility/speed for dramatically lower storage and operational cost at scale — a common reason teams already using Prometheus/Grafana adopt Loki specifically, since the labeling model and toolchain feel consistent with what they already run for metrics.

### 18. How would you design alerting to minimize alert fatigue while still catching real problems?
Alert on **symptoms that actually matter to users** (SLO burn rate, elevated error rate/latency actually affecting requests) rather than on every possible internal cause independently (alerting separately on CPU, memory, disk, *and* the user-facing symptom those causes might produce is redundant and noisy — the causes are useful for *diagnosis* once paged, not as independent page triggers themselves). Use multi-window, multi-burn-rate alerting for SLO-based alerts (a very fast burn rate over a short window pages immediately for a severe, fast-developing problem; a slower burn rate over a longer window pages less urgently, for a slow, sustained degradation) rather than one single naive threshold. Route alerts by actual actionability and urgency (page only for things requiring immediate human action; route lower-urgency signals to a dashboard/ticket instead of a page) and regularly review/prune alerts that fire often but rarely correspond to real actionable problems — a team that has learned to reflexively dismiss pages has an alerting system that has already failed at its actual job, regardless of how technically correct each individual alert rule is.

### 19. What's the difference between a "black-box" and "white-box" monitoring approach?
**Black-box** monitoring observes a system from the outside, the way a user/consumer would — synthetic HTTP checks hitting a public endpoint, uptime checks (Blackbox Exporter, Pingdom) — it directly measures what users actually experience, but can't tell you *why* something is failing internally. **White-box** monitoring instruments the system's internals directly (application-emitted metrics, internal queue depths, per-function timing) — far richer for root-cause diagnosis, but requires the system to actually be instrumented, and doesn't by itself prove the user-facing experience is actually healthy (an internal metric can look fine while the actual customer-facing path is broken for a reason the internal instrumentation didn't anticipate). Mature observability uses both — black-box as the ground-truth "is the user actually okay" signal, white-box for diagnosing why once black-box or SLO-based signals indicate a problem.

## Senior Level (5+ yrs)

### 20. Design an observability strategy for a large microservices platform (50+ services, multiple teams) from scratch — what do you standardize centrally vs. leave to individual teams?
Standardize centrally: a common structured-logging schema/format (so cross-service log correlation actually works — every service should at minimum emit a consistent trace ID, timestamp format, and severity field), a shared distributed tracing instrumentation approach (OpenTelemetry as the vendor-neutral standard, auto-instrumented at the framework/service-mesh level wherever possible so individual teams don't each have to hand-instrument tracing correctly), a common metrics-naming/labeling convention (to avoid inconsistent, colliding, or high-cardinality-prone metric names across teams), and a centrally-operated observability backend (Prometheus/Thanos or a managed equivalent, a log aggregation platform, a tracing backend) so every team isn't independently standing up and operating their own stack. Leave to individual teams: which specific application-level metrics/dashboards matter for their service's own business logic, their own SLO targets appropriate to their service's actual criticality (not a one-size-fits-all SLO across services with very different importance), and their own alert thresholds/routing tuned to their team's on-call reality — centralizing the *plumbing and conventions* while leaving the *judgment about what matters for this specific service* to the team that actually owns and understands it is the balance that scales without either fragmenting into 50 incompatible observability stacks or forcing an ill-fitting one-size-fits-all policy onto every team.

### 21. How would you approach the cost of observability data itself at scale (metrics cardinality, log volume, trace sampling) without sacrificing the ability to debug real incidents?
For metrics, actively govern cardinality (linting/blocking unbounded labels before they ship, via metric-naming review or automated cardinality-limiting proxies like Grafana's Adaptive Metrics or Prometheus's `keep_dropped_targets`/relabeling rules) rather than discovering the cost problem only after a high-cardinality metric has already degraded the system. For logs, apply level-based and sampling-based volume control in production (not logging at DEBUG by default, sampling extremely high-volume, low-value log lines) while ensuring error/warning-level and business-critical events are never sampled away — losing the one log line that would have explained an incident to save a small fraction of storage cost is a bad trade. For traces, use **tail-based sampling** where feasible (deciding whether to keep a trace *after* seeing how it completed — always keeping traces that errored or were unusually slow, while sampling down the large volume of uninteresting, fast, successful traces) rather than naive head-based sampling (deciding to sample before knowing the outcome), since tail-based sampling preserves exactly the traces most valuable for debugging while still controlling overall volume/cost. Across all three, the guiding principle is *shape* the volume down intelligently (keep the rare, anomalous, and error-related signal at full fidelity; aggressively reduce the redundant high-volume "everything is fine" signal) rather than uniformly throttling everything, which risks losing precisely the data you'll need during the next real incident.

### 22. Walk through designing SLOs for a set of services with genuinely different criticality (a core payment API vs. an internal admin tool), and how error budgets should actually influence team behavior day to day.
SLO targets should reflect actual business impact and user expectations, not a uniform policy applied indiscriminately — a payment API might warrant a demanding 99.95%+ availability SLO with tight latency targets (real revenue/trust impact per minute of degradation), while an internal admin tool used by a handful of employees during business hours might reasonably have a much looser SLO (99% availability, wider latency tolerance) reflecting its genuinely lower criticality — setting both to the same aggressive target wastes engineering effort on the low-criticality service and creates alert/on-call burden disproportionate to actual impact. Error budgets should be a real, followed input to planning decisions, not a metric nobody actually acts on: a documented, pre-agreed policy (ideally set before a crisis, not negotiated during one) that when a service's error budget is nearly exhausted, the team actually pauses risky changes/feature releases to that service and prioritizes reliability work until the budget recovers — the value of an error-budget policy comes specifically from it being a pre-committed, non-negotiated-in-the-moment agreement between the team and its stakeholders (including product/business stakeholders who might otherwise push back on delaying a feature for "just an SLO number"), since without that pre-commitment, error budgets become a metric on a dashboard nobody actually lets change real prioritization decisions.
