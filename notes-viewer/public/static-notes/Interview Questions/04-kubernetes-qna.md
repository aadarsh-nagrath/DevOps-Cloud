## Junior Level (0–2 yrs)

### 1. What is Kubernetes, and what problem does it solve?
Kubernetes (K8s) is an open-source container orchestration platform that automates deploying, scaling, healing, and networking containerized applications across a cluster of machines. It solves the operational problems that appear once you have more than a handful of containers: scheduling them onto available capacity, restarting them when they crash, rolling out updates without downtime, load-balancing traffic across replicas, and managing configuration/secrets — all declaratively instead of via manual scripts.

### 2. What is the difference between a Pod, a container, and a node?
A **container** is a single running application process (as covered in the Docker section). A **Pod** is Kubernetes' smallest deployable unit — a group of one or more containers that share the same network namespace (same IP, `localhost` between them) and can share storage volumes; most Pods run exactly one container, with multiple only for tightly-coupled sidecar patterns. A **node** is a physical or virtual machine (worker) in the cluster that actually runs Pods, managed by the control plane.

### 3. What is the Kubernetes control plane, and what are its main components?
The control plane is the cluster's "brain," making global decisions and reacting to cluster state. Key components: **kube-apiserver** (the front door — all interaction, including `kubectl`, goes through its REST API), **etcd** (the distributed key-value store holding all cluster state), **kube-scheduler** (decides which node a new Pod should run on), and **kube-controller-manager** (runs the control loops — Deployment controller, Node controller, etc. — that continuously reconcile actual state toward desired state).

### 4. What runs on a worker node?
**kubelet** (the agent that talks to the API server and ensures containers described in assigned PodSpecs are actually running, reporting node/pod status back), **kube-proxy** (maintains network rules on the node so Services can route traffic to the right Pods), and the **container runtime** (containerd or CRI-O, implementing the Container Runtime Interface that actually pulls images and runs containers).

### 5. What is a Deployment, and how is it different from directly creating a Pod?
A Deployment is a higher-level object that manages a ReplicaSet, which in turn manages a set of identical Pod replicas — declaratively describing "I want N copies of this Pod spec running, always." If you create a bare Pod directly and it crashes or its node dies, nothing recreates it. A Deployment continuously reconciles: if a Pod dies, the ReplicaSet notices the actual count is below desired and creates a replacement; Deployments also manage rolling updates and rollbacks, which bare Pods/ReplicaSets don't handle on their own.

### 6. What is a Service, and why do Pods need one instead of just using Pod IPs directly?
Pod IPs are ephemeral — a Pod gets a new IP every time it's recreated (crash, rescheduling, rolling update). A **Service** provides a stable virtual IP and DNS name that automatically load-balances traffic across whichever Pods currently match its label selector, regardless of Pod churn — so other workloads can reliably reach "the backend service" without tracking individual Pod IPs themselves.

### 7. What are the main Service types (`ClusterIP`, `NodePort`, `LoadBalancer`, `ExternalName`)?
`ClusterIP` (the default) exposes the Service only inside the cluster, on an internal virtual IP. `NodePort` additionally exposes it on a static port on every node's IP, reachable from outside the cluster. `LoadBalancer` provisions an external cloud load balancer (AWS ELB/NLB, GCP LB, etc.) that routes to the Service — the standard way to expose a Service to the internet on a cloud provider. `ExternalName` maps the Service to an external DNS name (a CNAME), with no proxying involved at all — useful for referencing an external database or API by an internal, cluster-consistent name.

### 8. What is a namespace in Kubernetes, and why use multiple namespaces?
A namespace is a virtual, logical partition within a single physical cluster, scoping names (two objects can share a name if they're in different namespaces) and often used as a boundary for RBAC permissions, resource quotas, and network policies. Common patterns: one namespace per environment (`dev`, `staging`, `prod`) or per team/application — though note namespaces are *not* a strong security boundary on their own (Pods across namespaces can reach each other over the network by default unless NetworkPolicies restrict it).

### 9. What is a ConfigMap, and how is it different from a Secret?
Both decouple configuration from container images, injectable into Pods as environment variables or mounted files. A **ConfigMap** holds non-sensitive configuration (feature flags, config file contents, URLs). A **Secret** holds sensitive data (passwords, tokens, TLS certs) — stored base64-*encoded* (not encrypted) by default in `etcd`, so a Secret is not meaningfully more "secure" than a ConfigMap unless you separately enable encryption-at-rest for `etcd` and tightly control RBAC access to Secrets.

### 10. What is a Label and a Selector, and how do they relate?
A **label** is an arbitrary key-value pair attached to an object (`app: frontend`, `env: prod`) for identification/organization. A **selector** is a query against those labels (`app=frontend`) used by Services, Deployments, and other controllers to determine which set of objects they should act on — this loose, label-based coupling (rather than direct references) is a core Kubernetes design principle, letting you regroup/retarget objects just by changing labels.

### 11. What's the difference between `kubectl apply` and `kubectl create`?
`kubectl create` imperatively creates a new object from a manifest and fails if it already exists. `kubectl apply` is declarative — it creates the object if it doesn't exist, or computes and applies a diff/patch against the live object if it does, making it safe to re-run repeatedly (idempotent), which is why `apply` is the standard command for GitOps/CI-driven deployments rather than `create`.

### 12. What does `kubectl get pods`, `kubectl describe pod`, and `kubectl logs` each tell you, and when do you reach for each?
`kubectl get pods` gives a quick, high-level status list (name, ready count, status, restarts, age) — your first look at "is anything obviously wrong." `kubectl describe pod <name>` gives full details plus, critically, the **Events** section at the bottom, showing scheduling decisions, image pull issues, and probe failures — the first place to look when a Pod won't start. `kubectl logs <pod> [-c container] [-f] [--previous]` shows the container's stdout/stderr — `--previous` is essential for a crash-looping container, since it shows the logs from the *last* (crashed) instance rather than the fresh, empty logs of the just-restarted one.

### 13. What is a ReplicaSet?
A ReplicaSet ensures a specified number of identical Pod replicas (matching a label selector) are running at any given time, creating or deleting Pods as needed to reconcile actual vs. desired count. In practice you rarely create ReplicaSets directly — you create a Deployment, which creates and manages ReplicaSets for you (one per revision, enabling rolling updates and rollback).

### 14. What is a rolling update, and how does a Deployment perform one?
A rolling update replaces Pods running the old version with the new version incrementally, rather than all at once, avoiding downtime. The Deployment creates a *new* ReplicaSet for the new version and gradually scales it up while scaling the old ReplicaSet down, governed by `maxSurge` (how many extra Pods above desired count are allowed during the rollout) and `maxUnavailable` (how many Pods can be unavailable at once) — `kubectl rollout status deployment/<name>` tracks progress, and `kubectl rollout undo deployment/<name>` rolls back to the previous ReplicaSet's spec if something goes wrong.

### 15. What are readiness probes and liveness probes, and how are they different?
A **liveness probe** answers "is this container still healthy, or should it be restarted?" — a failing liveness probe causes `kubelet` to kill and restart the container. A **readiness probe** answers "is this container ready to receive traffic right now?" — a failing readiness probe removes the Pod from a Service's load-balancing pool *without* restarting it (useful during slow startup, or temporary overload, where restarting wouldn't help and would only make things worse). Both can be defined via `httpGet`, `tcpSocket`, `exec`, or (since 1.23+ GA) `grpc` checks.

### 16. What happens when you delete a Pod that's managed by a Deployment?
The Deployment's ReplicaSet controller notices the actual replica count dropped below the desired count and immediately creates a new Pod to replace it — you can't "permanently" delete one Pod out of a Deployment this way, since the controller's whole job is to keep reconciling toward the desired count. To actually reduce the count, you scale the Deployment down (`kubectl scale deployment/<name> --replicas=2`) or delete the Deployment itself.

### 17. What is `kubectl port-forward`, and when would you use it?
`kubectl port-forward pod/<name> 8080:80` (or against a Service/Deployment) tunnels a local port on your machine directly to a port inside a specific Pod, without needing a Service, Ingress, or any cluster-external exposure — extremely useful for quickly debugging a Pod (hitting its API/metrics endpoint, connecting to a database Pod) from your laptop without changing any cluster configuration.

### 18. What is a StatefulSet, and how is it different from a Deployment?
A Deployment treats Pods as interchangeable — any replica can be replaced by any other, with no stable identity. A **StatefulSet** is for workloads needing stable, unique network identity and/or stable storage per replica (databases, message queues) — each Pod gets a predictable, persistent name (`web-0`, `web-1`, `web-2`, not random suffixes), is created/scaled/deleted in strict order, and (typically paired with `volumeClaimTemplates`) each replica keeps its *own* persistent volume across restarts/rescheduling, rather than sharing one or getting a fresh one.

### 19. What is a DaemonSet, used for what kind of workload?
A DaemonSet ensures exactly one copy of a Pod runs on every node (or a filtered subset of nodes) in the cluster, automatically adding a Pod when a new node joins. Typical use cases: log collection agents (Fluentd/Fluent Bit), node-level monitoring agents (node-exporter), and CNI/networking components that must run on every node by nature.

### 20. What is a Job and a CronJob?
A **Job** creates one or more Pods and ensures a specified number of them run to *successful completion* (unlike a Deployment, which keeps Pods running indefinitely) — used for batch/one-off tasks like a database migration. A **CronJob** creates Jobs on a recurring schedule using standard cron syntax (`0 2 * * *`) — used for scheduled batch work like nightly reports or backups.

## Mid Level (2–5 yrs)

### 21. Walk through exactly what happens from `kubectl apply -f pod.yaml` to the container actually running.
`kubectl` sends the manifest as a request to the **kube-apiserver**, which authenticates/authorizes it, runs it through admission controllers (validating/mutating webhooks), and persists the desired object into **etcd**. The **scheduler**, watching for unscheduled Pods, evaluates node capacity/affinity/taints and binds the Pod to a specific node by updating its `spec.nodeName`. The **kubelet** on that node, watching the API server for Pods assigned to it, sees the new binding and instructs the **container runtime** (via the CRI) to pull the image and start the container(s), then continuously reports the Pod's actual status back to the API server, which is what `kubectl get pods` reflects.

### 22. Explain the Kubernetes networking model — what must be true about Pod-to-Pod communication cluster-wide?
The fundamental requirement (enforced by whatever CNI plugin is installed, not by Kubernetes core itself): every Pod gets its own unique IP, and every Pod can reach every other Pod's IP directly, cluster-wide, *without NAT* — regardless of which node either is on. This "flat network" model is what lets application code treat Pod communication uniformly, without needing to know or care about node topology. CNI plugins (Calico, Cilium, Flannel, AWS VPC CNI) each implement this requirement differently (overlay networks via VXLAN, BGP-based routing, or direct VPC-native IP assignment), which is exactly why the CNI is pluggable rather than baked into Kubernetes itself.

### 23. What is `kube-proxy`, and how does it actually route traffic to a Service's backend Pods?
`kube-proxy` runs on every node and watches the API server for Service/Endpoint changes, translating them into local packet-forwarding rules — historically via `iptables` DNAT rules (rewriting the Service's virtual IP to a randomly-selected backend Pod IP), and increasingly via `IPVS` mode (better performance at very high Service/endpoint counts) or eBPF-based dataplanes (e.g. when using Cilium in kube-proxy-replacement mode). Either way, this happens entirely at the packet-forwarding layer on each node — there's no separate proxy process actually in the data path for every request.

### 24. What is an Ingress, and how is it different from a Service of type `LoadBalancer`?
A `LoadBalancer` Service provisions one cloud load balancer *per Service*, operating at L4 (TCP/UDP) — fine for a handful of services, but expensive and unwieldy at scale (one cloud LB per service). An **Ingress** is an L7 (HTTP/HTTPS) routing object that lets a *single* entry point (backed by one Ingress Controller, e.g. NGINX, Traefik, or a cloud-native one like AWS Load Balancer Controller) route to many different Services based on hostname/path rules, and typically also handles TLS termination — the standard way to expose multiple HTTP services cost-effectively.

### 25. What rules would you actually configure in an Ingress resource, and why use a dedicated Ingress Controller rather than exposing Services directly?
A typical Ingress manifest configures: `host`-based rules (routing `api.example.com` to one Service and `app.example.com` to another, from a single shared entry point/IP), `path`-based rules within a host (`/api` to a backend Service, `/` to a frontend Service, using `pathType: Prefix` or `Exact`), a `tls` block referencing a Secret holding the certificate/key for TLS termination at the edge, and annotations specific to whichever Ingress Controller you're running (e.g. NGINX Ingress annotations for rewrite rules, rate limiting, or body-size limits — these aren't part of the core Ingress spec itself, which is why Ingress behavior varies somewhat by controller). You need a dedicated Ingress *Controller* (NGINX, Traefik, AWS Load Balancer Controller, etc.) because the Ingress *resource* itself is just a declarative routing specification — nothing in the cluster actually proxies traffic based on it until a controller is running, watching Ingress objects, and programming its own data plane (an actual NGINX/Envoy process, or a cloud ALB) to match; without a controller installed, creating Ingress objects has literally no effect on traffic at all.

### 26. Walk through exactly how traffic flows from an external client to a specific Pod in Kubernetes.
External request hits the cluster's entry point first — typically a cloud load balancer (provisioned by a `LoadBalancer` Service or, more commonly for HTTP, by an Ingress Controller's own Service) sitting in front of the cluster, which forwards the connection to one of the cluster's nodes. From there, if it's an Ingress-routed HTTP request, it reaches the Ingress Controller's own Pod (itself just a Pod running nginx/Envoy, fronted by its own Service), which inspects the request's host/path, matches it against configured Ingress rules, and forwards it to the matching backend Service's ClusterIP. That Service's ClusterIP isn't itself a listening process — `kube-proxy`'s packet-forwarding rules (iptables/IPVS/eBPF, programmed from the Service's Endpoints) intercept traffic addressed to that virtual IP and DNAT it directly to one specific backend Pod's actual IP, selected from the set of Pods currently matching the Service's label selector and passing their readiness probe. The response takes the reverse path back out. The key insight interviewers are checking for: a Service's ClusterIP is a routing abstraction implemented via per-node packet-rewriting rules, not a real listening server anywhere — the actual TCP connection, after DNAT, terminates directly at the chosen Pod.

### 27. How do you scale the number of Pods in a Deployment while still guaranteeing a minimum number of replicas stays available?
For manual/fixed scaling, `kubectl scale deployment/<name> --replicas=N` directly sets the desired count, and the Deployment/ReplicaSet controller reconciles toward it — but a plain replica count alone says nothing about availability *during* a rollout or voluntary disruption (a node drain, a cluster upgrade). Two separate mechanisms guarantee a floor beyond just "replicas: N": a **PodDisruptionBudget** (`minAvailable: 3` or `maxUnavailable: 1`) constrains voluntary evictions (node drains, cluster-autoscaler scale-downs) so the eviction API refuses to remove a Pod if doing so would breach the budget — this doesn't protect against involuntary disruption (a node crashing outright), only voluntary/API-driven evictions. For automatic, load-driven scaling with a floor, a **Horizontal Pod Autoscaler** scales replicas between an explicit `minReplicas` and `maxReplicas` based on observed metrics — `minReplicas` is the actual floor the HPA will never scale below regardless of how low load drops, which is the direct answer to "maintaining a minimum" when scaling is automatic rather than a fixed manual count.

### 28. What's the difference between requests and limits in a Pod's resource spec, and why does it matter for scheduling and stability?
`resources.requests` is what the scheduler *guarantees* is reserved for the container when deciding which node to place it on (a node won't be chosen if it can't satisfy the sum of requests of everything already scheduled there). `resources.limits` is the hard ceiling the container is *not allowed to exceed* at runtime — exceeding a CPU limit results in throttling; exceeding a memory limit results in an OOM-kill of that container. Setting requests too low relative to actual usage causes node overcommitment and noisy-neighbor problems; setting limits too low causes throttling/OOMKills even when the node has spare capacity — right-sizing both from real usage data (e.g. via VPA recommendations or historical metrics) is a core ongoing operational task.

### 29. What are Quality of Service (QoS) classes in Kubernetes, and how are they determined?
Kubernetes assigns each Pod one of three QoS classes based on its requests/limits: **Guaranteed** (every container has requests == limits, for both CPU and memory — highest protection, last to be evicted under node pressure), **Burstable** (at least one container has requests set, but requests != limits — evicted before Guaranteed Pods), and **BestEffort** (no requests or limits set at all — first to be evicted under any resource pressure). This directly determines eviction order when a node runs low on resources, so it's a real design lever, not just a label.

### 30. What is a Horizontal Pod Autoscaler (HPA), and how is it different from a Vertical Pod Autoscaler (VPA) and Cluster Autoscaler?
**HPA** scales the *number of Pod replicas* up/down based on observed metrics (CPU/memory utilization by default, or custom/external metrics via the metrics API) against a target Deployment/StatefulSet. **VPA** instead adjusts the *resource requests/limits* of existing Pods (recommending or automatically applying new values) rather than changing replica count — useful for right-sizing single-instance or hard-to-horizontally-scale workloads. **Cluster Autoscaler** operates one level up, adding or removing entire *nodes* from the cluster when Pods can't be scheduled due to insufficient capacity, or when nodes are underutilized — HPA/VPA and Cluster Autoscaler are complementary, commonly all three run together.

### 31. Explain taints and tolerations, and how they differ from node affinity.
A **taint** on a node (`kubectl taint nodes node1 key=value:NoSchedule`) repels Pods from scheduling there *unless* the Pod has a matching **toleration** — this is a node-driven mechanism ("I refuse most Pods unless they explicitly opt in," e.g. dedicating nodes to GPU workloads). **Node affinity** is the inverse direction — a Pod-driven mechanism expressing "I prefer/require nodes with these labels" — without an affinity rule, a Pod is happy to run anywhere that has no taint blocking it. Taints/tolerations and affinity are often combined: taint the special nodes *and* add matching tolerations plus affinity to the specific Pods that should land there, so ordinary Pods are both repelled (taint) and never even try to go there (no matching affinity needed, but the taint alone is often sufficient).

### 32. What is a PersistentVolume (PV) and a PersistentVolumeClaim (PVC), and how do they relate to StorageClasses?
A **PV** is a piece of actual storage in the cluster (an AWS EBS volume, an NFS share, etc.), provisioned either manually or dynamically. A **PVC** is a *request* for storage made by a user/Pod ("I need 10Gi, ReadWriteOnce") — Kubernetes binds a PVC to a matching PV. A **StorageClass** defines *how* to dynamically provision a PV when a PVC requests one (which provisioner/backend, what parameters like disk type/IOPS) — without dynamic provisioning via a StorageClass, an administrator would have to manually pre-create PVs to match every PVC, which doesn't scale operationally.

### 33. What is RBAC in Kubernetes, and what's the difference between a Role and a ClusterRole, and a RoleBinding and a ClusterRoleBinding?
RBAC (Role-Based Access Control) governs who can do what against the API server. A **Role** grants permissions (verbs like `get`/`list`/`create`/`delete` on resources like `pods`/`deployments`) scoped to a single namespace. A **ClusterRole** grants permissions cluster-wide, or against cluster-scoped resources (nodes, PVs) that have no namespace at all — it can also be *bound* within just one namespace via a RoleBinding, which is a common pattern for reusing a common permission set across many namespaces. A **RoleBinding** attaches a Role (or ClusterRole) to specific users/groups/ServiceAccounts within one namespace; a **ClusterRoleBinding** does the same cluster-wide.

### 34. What is a ServiceAccount, and how does a Pod use one to authenticate to the Kubernetes API?
A ServiceAccount is an identity for processes running *inside* the cluster (as opposed to human users, who authenticate differently). Every Pod is assigned a ServiceAccount (the namespace's `default` one, unless specified otherwise), and its credentials (a projected, automatically-rotated token since Kubernetes 1.22+, mounted at `/var/run/secrets/kubernetes.io/serviceaccount/`) are what any in-cluster code (like a controller or an app calling the K8s API) uses to authenticate — RBAC rules are then bound to that ServiceAccount to control exactly what it's permitted to do.

### 35. What's the difference between a NetworkPolicy's `ingress` and `egress` rules, and what happens if a namespace has zero NetworkPolicies?
`ingress` rules control what's allowed to connect *to* Pods matching the policy's selector; `egress` rules control what those Pods are allowed to connect *out to*. With **zero** NetworkPolicies applied to a Pod, the default is fully permissive — any Pod can talk to any other Pod, in any namespace, with no restriction at all (this surprises people who assume Kubernetes is "secure by default" on the network layer — it isn't, until you explicitly apply policies, and the CNI plugin must actually support NetworkPolicy enforcement in the first place, which not all of them do out of the box).

### 36. A Pod is stuck in `Pending` state. Walk through how you'd diagnose why.
`kubectl describe pod <name>` and read the **Events** section — this almost always states the reason directly: "Insufficient cpu/memory" (no node has enough allocatable resources left), "node(s) had taints that the pod didn't tolerate," "0/5 nodes are available: node affinity/selector didn't match," or a PVC that can't be bound (no matching PV or StorageClass provisioner issue). `Pending` specifically means the scheduler hasn't been able to bind the Pod to *any* node yet, so the investigation is almost always about node capacity, scheduling constraints, or unmet storage/networking prerequisites — not about the container itself (which hasn't even started).

### 37. A Pod is stuck in `CrashLoopBackOff`. Walk through how you'd diagnose why.
`CrashLoopBackOff` means the container *starts*, then exits (crashes), and Kubernetes is repeatedly restarting it with exponential backoff. `kubectl logs <pod> --previous` shows the crashed instance's actual output (the current attempt's logs are often empty since it just restarted) — the most common causes are an application error/misconfiguration causing immediate exit, a missing dependency (can't connect to a database at startup and the app doesn't retry, it just exits), a failing liveness probe repeatedly killing an otherwise-slow-to-start container, or (check `kubectl describe pod` for the exit code) an OOMKill (exit code 137) if it's a memory limit issue rather than an application logic issue.

### 38. What's the difference between `ImagePullBackOff` and `ErrImagePull`, and common root causes?
`ErrImagePull` is the immediate, first-attempt failure to pull an image; `ImagePullBackOff` is Kubernetes backing off and retrying after that initial failure. Common causes: a typo in the image name/tag, the image genuinely doesn't exist at that tag, missing or incorrect `imagePullSecrets` for a private registry, or (less obviously) the node's container runtime hitting a registry rate limit (a well-known issue with unauthenticated Docker Hub pulls at scale) — `kubectl describe pod` again shows the exact underlying error message from the runtime.

### 39. How do you perform a zero-downtime rolling restart of a Deployment without changing its image/config?
`kubectl rollout restart deployment/<name>` triggers a rolling replacement of all Pods (useful for picking up a changed ConfigMap/Secret that isn't automatically re-read by running Pods, or just cycling Pods for other operational reasons) using the same rolling-update mechanics (`maxSurge`/`maxUnavailable`) as a normal update — as long as readiness probes are correctly configured, traffic is never sent to a Pod before it's actually ready, giving a genuinely zero-downtime restart.

### 40. What's the difference between `emptyDir`, `hostPath`, and a PersistentVolume-backed volume?
`emptyDir` is ephemeral, Pod-lifetime-scoped scratch storage — created empty when the Pod starts, deleted permanently when the Pod is removed (useful for scratch space or sharing files between containers in the same Pod). `hostPath` mounts a path directly from the *node's* filesystem into the Pod — tightly couples the Pod to whichever specific node it lands on and is generally discouraged for application workloads (mostly used by system-level DaemonSets that genuinely need node filesystem access). A PV-backed volume (via a PVC) is durable, decoupled from any specific Pod or node, and is what you actually want for persistent application data.

## Senior Level (5+ yrs)

### 41. Explain the full Kubernetes reconciliation/controller pattern, and why "declarative, level-triggered" design is more robust than an imperative, event-triggered one.
Every controller runs a continuous loop: observe current state (via the API server, typically using informers/watches for efficiency rather than polling), compare it against desired state, and take action to reconcile any difference — repeated indefinitely, not just once in response to a single event. This "level-triggered" design (react to *current state*, not to *the specific event that changed it*) is robust because it self-heals from missed events, restarts, or race conditions — if a controller crashes and misses ten events, it doesn't matter, because on restart it just re-evaluates current-vs-desired state fresh and takes whatever action is still needed. An event-triggered ("edge-triggered") design, by contrast, would need every single transition event delivered reliably and processed in order, which is much harder to guarantee correctly at scale, especially across restarts and network partitions.

### 42. Design a multi-tenant Kubernetes cluster strategy for several internal teams with different trust levels. What isolation mechanisms would you layer, and where are the real boundaries?
Namespaces alone provide organizational/RBAC scoping but are not a strong isolation boundary — Pods across namespaces share the same kernel on shared nodes unless you do more. A real multi-tenant design layers: RBAC scoped tightly per-namespace per-team; ResourceQuotas and LimitRanges per namespace to prevent one tenant from starving others; NetworkPolicies (default-deny ingress/egress per namespace, explicit allow-lists) since Kubernetes networking is flat/open by default; PodSecurityStandards/admission control (restricted profile) to prevent privilege escalation, host namespace access, or privileged containers; and, for genuinely untrusted or higher-risk tenants, dedicating separate node pools (via taints/tolerations + node affinity) or even separate clusters entirely, since sharing a kernel via `runc` is fundamentally weaker isolation than a hypervisor boundary — the honest answer to "is namespace-based multi-tenancy secure" is "it raises the bar significantly but is not equivalent to hard tenant isolation," and the risk tolerance of the actual tenants should drive how far up that ladder (shared nodes → dedicated node pools → separate clusters → separate cloud accounts) you go.

### 43. Walk through diagnosing a cluster-wide issue where many unrelated Pods across the cluster start failing readiness probes simultaneously.
Given the "simultaneous, cluster-wide, unrelated workloads" pattern, suspect a shared-infrastructure cause rather than N independent application bugs: check `kube-apiserver` health/latency first (probes failing because the apiserver itself, or `etcd` behind it, is under load/unavailable can manifest as widespread probe timeouts if probes or their dependencies route through cluster DNS/API calls); check CoreDNS health and DNS resolution latency cluster-wide (a very common systemic cause — if application health checks or their dependencies rely on DNS and CoreDNS is degraded/overloaded, everything downstream looks broken simultaneously); check node-level resource pressure across the fleet (if many nodes are simultaneously CPU-throttled or under memory pressure, e.g. from a bad node-level DaemonSet rollout or a runaway cron job, probes cluster-wide can start timing out due to CPU starvation rather than any application-level fault); and check whether a recent cluster-level change correlates in time (a CNI upgrade, a node pool rotation, an admission webhook that started rejecting/delaying requests) rather than assuming it's coincidental that everything broke at once.

### 44. How does the Kubernetes scheduler actually decide where to place a Pod, in more depth than "it picks a node with capacity"?
Scheduling happens in two phases: **filtering** (find the set of nodes that satisfy hard constraints — sufficient resources, matching node selectors/affinity/taints-tolerations, volume topology constraints) and **scoring** (rank the filtered/feasible nodes using a set of weighted priority functions — spreading Pods across nodes/zones for availability, bin-packing to consolidate for efficiency, preferring nodes that already have the required image cached, honoring inter-pod affinity/anti-affinity preferences) and finally binds the Pod to the highest-scoring node. Custom scheduling needs (specialized bin-packing, GPU topology awareness, cost-aware placement) are handled via scheduler extenders, a custom scheduler plugin using the Scheduling Framework, or in some cases running an entirely separate custom scheduler for specific workload classes, selected per-Pod via `spec.schedulerName`.

### 45. Explain etcd's role in cluster reliability, and what an operator needs to know about it beyond "it's the database."
`etcd` is a distributed, Raft-consensus-based key-value store holding the entire cluster's state — every object, every status update, goes through it, making it the single most critical stateful component in a cluster (if `etcd` is lost with no backup, the cluster's control-plane state is unrecoverable even if all workload nodes are fine). Operationally: it requires low-latency, low-jitter disk I/O (SSD, ideally dedicated) since Raft consensus is latency-sensitive and a slow disk causes leader elections/instability under load; it should run as an odd-numbered cluster (3 or 5 members) for quorum tolerance; regular, tested (not just taken-and-forgotten) snapshots/backups are essential, since `etcd` corruption or majority member loss is one of the few Kubernetes failure modes with no automatic self-healing path; and its size/performance degrades with very large numbers of objects or excessive `watch` load, which is why very large clusters need explicit `etcd` capacity planning, not just node capacity planning.

### 46. What is the Container Storage Interface (CSI) and Container Network Interface (CNI), and why does this plugin architecture matter for how you evaluate a managed Kubernetes offering?
CSI and CNI are standardized interfaces that decouple Kubernetes core from any specific storage or networking implementation — any storage vendor/cloud can implement a CSI driver (AWS EBS CSI, Azure Disk CSI, Portworx) and any networking vendor can implement a CNI plugin (Calico, Cilium, AWS VPC CNI) without Kubernetes core needing to know about vendor specifics. This matters practically because "Kubernetes" behavior around networking (NetworkPolicy support, IP-per-Pod vs. overlay, performance) and storage (supported access modes, snapshot/resize capability, failure domains) varies significantly by *which* CNI/CSI a given managed offering defaults to or supports — so evaluating a managed Kubernetes service (EKS, GKE, AKS) or a specific cluster design genuinely requires looking one layer below "it's Kubernetes" into exactly which CNI/CSI implementation is in play and what it actually supports.

### 47. Design an upgrade strategy for a large, business-critical multi-cluster Kubernetes fleet, addressing version skew, testing, and rollback.
Maintain a documented, tested upgrade path following Kubernetes' supported version-skew policy (control plane can be up to a few minor versions ahead of kubelets, but not arbitrarily so) — never skip more minor versions than officially supported in one jump. Stage upgrades through environments (a canary/non-production cluster first, running real synthetic or shadow traffic, then a low-risk production cluster, then the rest) rather than upgrading every cluster simultaneously. Automate the control-plane and node-pool upgrade sequence (for managed offerings, this is largely provider-driven; for self-managed, tools like `kubeadm` plus careful node draining) with health verification gates between steps, and always read the release notes for deprecated/removed API versions *before* upgrading (a common real-world break: manifests still using an API version that was removed in the target release — `kubectl-convert` and `pluto`/`kube-no-trouble` help catch these ahead of time). Rollback for a control-plane upgrade is generally much harder than rollback for an application deployment (Kubernetes doesn't support downgrading the control plane cleanly in most cases), so the actual safety net is heavy pre-upgrade validation and canarying, not "roll back if it breaks."

### 48. How would you reason about and reduce the blast radius of a compromised Pod in a cluster you're responsible for securing?
Layer controls so a compromise of one Pod doesn't cascade: run as non-root with a read-only root filesystem and dropped capabilities (limits what the compromised process can even attempt); apply the `restricted` Pod Security Standard to prevent privilege escalation and host-namespace access in the first place; default-deny NetworkPolicies so a compromised Pod can't freely reach other Pods, the cloud metadata endpoint (a very common real-world pivot point to steal cloud IAM credentials — worth explicitly blocking `169.254.169.254` egress unless required), or the internet for exfiltration/C2; scope its ServiceAccount's RBAC permissions to the absolute minimum it needs (a compromised Pod with a ServiceAccount that can `list secrets` cluster-wide turns a single-Pod compromise into a cluster-wide credential leak); and ensure runtime detection (Falco or similar, watching for anomalous syscalls/process execution inside containers) is in place so a compromise that does occur is actually noticed rather than persisting silently — no single one of these is sufficient alone, which is the point of defense-in-depth.

### 49. Your EKS cluster is experiencing pod `CrashLoopBackOff` issues. Walk through your debugging process end to end.
Same fundamentals as diagnosing `CrashLoopBackOff` on any cluster (see Q37), with a few EKS-specific angles added. Start with `kubectl describe pod <name>` for the Events section and `kubectl logs <pod> --previous` for the crashed instance's actual output — the most common root causes remain an application error on startup, a missing/unreachable dependency, a failing liveness probe prematurely killing a slow-starting container, or an OOMKill (exit code 137). EKS-specific checks layered on top: confirm the Pod's ServiceAccount has correctly configured IAM Roles for Service Accounts (IRSA) if it calls AWS APIs on startup — a very common EKS-specific crash cause is an application that fails fast because it can't authenticate to S3/RDS/Secrets Manager due to a missing or misconfigured IRSA trust policy/annotation, which looks identical to a generic startup crash in the logs until you specifically check the IAM side; check whether the node group/Fargate profile has sufficient capacity or is mid-scale-event (a Cluster Autoscaler or Karpenter scale-up lagging behind demand can manifest as Pods cycling while waiting on capacity, distinct from a true application crash); check the AWS VPC CNI's IP address allocation on the node (`ENI`/IP exhaustion on smaller instance types is a real EKS-specific failure mode that can prevent a Pod from ever getting a usable network namespace, surfacing as repeated failures that look crash-related); and check CloudWatch Container Insights/logs if the cluster is wired up to it, for a fleet-wide view correlating the crash against node-level or control-plane events around the same time, rather than only looking at the one Pod in isolation.

### 50. Your Pod keeps going into `CrashLoopBackOff`, but the logs show no errors. How would you approach debugging and resolution?
"No errors in the logs" is itself a clue: the process is either exiting *cleanly*, being killed from *outside*, or logging somewhere you're not looking (generic CrashLoopBackOff triage is in Q37). Start with `kubectl describe pod` and read `Last State: Terminated` — the **exit code and reason** matter more than the logs here. **Exit code 0 / `Completed`** means the main process simply finished: a shell-script entrypoint that returns, a server that daemonizes/forks into the background (PID 1 exits, so the container exits), or a `command`/`args` override that replaced the real entrypoint with something short-lived — fix it by running the process in the foreground (`nginx -g 'daemon off;'`, `exec "$@"` in entrypoint scripts). **Exit code 137 / `OOMKilled`** means the kernel killed it — the app never got the chance to log; raise the memory limit or fix the leak/heap sizing (e.g. JVM `-XX:MaxRAMPercentage`). **Exit 137 or 143 with "Liveness probe failed" in Events** means the kubelet is killing a healthy-but-slow container — add a `startupProbe` or fix the probe's path/port/timeout. Also check `kubectl logs --previous` (the *current* attempt is often empty), whether the app logs to a file instead of stdout/stderr, and `terminationMessagePath`. To reproduce interactively, create a debug copy with the entrypoint replaced so it stays up: `kubectl debug <pod> -it --copy-to=dbg --container=app -- sh`, then run the real command by hand and watch what happens; for distroless images use an ephemeral container (`kubectl debug -it <pod> --image=busybox --target=app`). Finally rule out environmental causes that produce silent exits: missing ConfigMap/Secret keys the app checks then quits on, wrong `securityContext` (non-root user can't write to a path), and missing env vars.

### 51. You have a StatefulSet with persistent volumes, and one Pod isn't being recreated properly after deletion. What could be the reasons, and how do you fix it without data loss?
StatefulSets guarantee *at most one* Pod per identity, and each ordinal is bound to its own PVC (`data-web-2` always goes to `web-2`), which causes most of the "stuck" cases. Common causes: (1) **Old Pod stuck `Terminating` on an unreachable node** — the controller won't create `web-2` again until the API confirms the old one is gone, to avoid two writers on one volume; on modern clusters apply the `node.kubernetes.io/out-of-service=nodeshutdown:NoExecute` taint (non-graceful node shutdown) so the Pod and its volume attachment are cleaned up safely, and only `--force --grace-period=0` delete once you're *certain* the node is really dead. (2) **`Multi-Attach error` / volume still attached** to the old node — an RWO EBS/PD volume can't attach to a new node until the old attachment is released (check `kubectl get volumeattachment`). (3) **Volume node affinity conflict** — EBS and other zonal disks live in one AZ; if no schedulable node exists in that AZ the Pod stays `Pending` (fix: capacity in that zone, node groups per AZ, `WaitForFirstConsumer` storage classes). (4) **`OrderedReady` pod management** — if `web-1` isn't Ready, `web-2` won't be created. (5) **A broken template after a bad rolling update** — reverting the template isn't always enough; you may have to delete the stuck Pod manually. (6) **PVC deleted / PV `Released`** — the new Pod creates a fresh empty PVC. To do this *without data loss*: never delete the PVC as part of troubleshooting; snapshot the volume (`VolumeSnapshot` or cloud snapshot) before any risky step; use `reclaimPolicy: Retain` for stateful storage classes so a deleted PVC doesn't delete the disk; and if a PV is stuck `Released`, clear its `spec.claimRef` and pre-create a PVC with the exact expected name (`<volumeClaimTemplate>-<sts>-<ordinal>`) bound to that PV so the Pod picks up the old data.

### 52. Your Cluster Autoscaler isn't scaling up even though Pods are `Pending`. What would you investigate?
Cluster Autoscaler only adds a node if it simulates that the Pending Pod *would schedule on a new node from some node group* — so most failures come down to "no node group could fit it" or "it can't change the node group." Check, in order: **Pod events** — CA writes `NotTriggerScaleUp: pod didn't trigger scale-up` with the reason per node group (e.g. `max node group size reached`, `node(s) didn't match Pod's node affinity/selector`, `Insufficient memory`). **Is it even a capacity problem?** A Pod pending on an unbound PVC, a missing image pull secret, or a scheduler issue won't be fixed by more nodes. **Pod bigger than any instance type** — a 64 Gi request in a node group of 32 Gi instances can never fit. **Constraints the node group template doesn't satisfy** — nodeSelectors, taints/tolerations, or zonal PVCs needing a specific AZ; when scaling from zero, the ASG needs `k8s.io/cluster-autoscaler/node-template/label/...` and `.../taint/...` tags so CA knows what a new node would look like. **Max size reached** on the ASG/node group. **Discovery and permissions** — auto-discovery tags (`k8s.io/cluster-autoscaler/enabled`, `k8s.io/cluster-autoscaler/<cluster-name>`) present, and CA's IAM role allowed `autoscaling:SetDesiredCapacity`/`DescribeAutoScalingGroups`. **Cloud-side failures** — the ASG's activity history may show `InsufficientInstanceCapacity`, an exhausted vCPU service quota, or subnets out of IPs; CA backs off a failing group for a while. **CA health itself** — `kubectl -n kube-system logs deploy/cluster-autoscaler` and the `cluster-autoscaler-status` ConfigMap, and check CA's version matches the cluster's minor version. On EKS, Karpenter avoids many of these (it picks instance types per Pod instead of using fixed node groups) — its logs and the `NodeClaim` objects are the equivalent places to look.

### 53. A NetworkPolicy is blocking traffic between services in different namespaces. How would you design and debug the policy so only specific paths are allowed?
**Design:** start from default-deny in each namespace (`podSelector: {}` with `policyTypes: [Ingress, Egress]`), then allow only the specific path you want — *both sides* need a rule if both namespaces default-deny egress/ingress. On the destination namespace, allow ingress from the exact source Pods in the exact source namespace, using the automatic `kubernetes.io/metadata.name` namespace label:
```yaml
ingress:
- from:
  - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: frontend}}
    podSelector: {matchLabels: {app: web}}      # same list item = AND
  ports: [{protocol: TCP, port: 8080}]
```
The classic bug is YAML indentation: putting a `-` before `podSelector` makes it a *separate* list item, which means OR ("any Pod in `frontend`, or any `app: web` Pod in *this* namespace") — either too open or not matching what you expected. On the source namespace, allow egress to that destination **and** egress to DNS (`kube-system`, `k8s-app: kube-dns`, UDP+TCP 53) — forgetting DNS is the most common reason "everything broke" after adding default-deny egress. Also remember policies target **Pod ports, not Service ports** (8080 on the container, not 80 on the Service). **Debug:** confirm the CNI actually enforces NetworkPolicy (Flannel doesn't; the AWS VPC CNI needs its network-policy agent enabled); `kubectl get netpol -A` and check each policy's `podSelector` really selects the Pods you think it does (`kubectl get pods -l app=web --show-labels`); test from a throwaway Pod with the source's labels (`kubectl run t --rm -it -n frontend -l app=web --image=nicolaka/netshoot -- curl -m3 api.backend:8080`), separating DNS failures from TCP failures; and use the CNI's flow visibility — Cilium Hubble (`hubble observe --verdict DROPPED`) or Calico flow logs — which tell you exactly which policy dropped the packet.

### 54. A microservice must connect to an external database over a VPN from inside the cluster. How would you architect this in Kubernetes with HA and security in mind?
First push back on the premise: the cleanest design is usually to **terminate the VPN at the network layer, not in the cluster** — an AWS Site-to-Site VPN or Direct Connect attached to the VPC/Transit Gateway (two tunnels across two AWS endpoints, BGP for failover), with route tables sending the DB's CIDR over the tunnel. Pods then reach the DB like any other routable IP, HA is the cloud provider's problem, and no Pod needs elevated privileges. If it truly must be in-cluster (no control of the VPC, per-tenant tunnels, etc.): run **dedicated VPN gateway Pods** (WireGuard/strongSwan) as a Deployment of ≥2 replicas spread across AZs (topology spread + PodDisruptionBudget), on a tainted node pool reserved for them, since they need `NET_ADMIN` — confine that capability to one namespace with Pod Security Admission and keep it *out* of application Pods (the per-Pod VPN sidecar approach spreads `NET_ADMIN` everywhere and multiplies tunnels, so avoid it). Route traffic to the gateway via a Service, and give the app a stable name for the DB with a selector-less Service + EndpointSlice (or `ExternalName`) so failover/IP changes don't touch app config. Health: liveness probes that actually check tunnel state (ping across the tunnel) so a dead tunnel restarts/fails over, and alerts on tunnel down. Security layers: NetworkPolicy so only the app's Pods can reach the gateway and only the gateway can egress to the VPN peer; VPN keys and DB credentials from a secrets manager (External Secrets Operator / Secrets Store CSI) and rotated; **TLS to the database anyway** — the VPN protects the network path, not the endpoint identity; least-privilege DB user per service; and connection pooling so a tunnel failover doesn't cause a reconnect storm.

### 55. You're running a multi-tenant platform on a single EKS cluster. How do you isolate workloads and ensure security, quotas, and observability per tenant?
Q42 covers the general isolation ladder; on EKS specifically, layer it like this. **Identity & access:** a namespace (or set, via Capsule/HNC) per tenant; EKS access entries mapped to Kubernetes RBAC Roles scoped to that tenant's namespaces only; per-tenant ServiceAccounts with **EKS Pod Identity or IRSA**, so each tenant's Pods get only their own AWS IAM permissions — and block access to the node's instance metadata (IMDSv2 with hop limit 1) so Pods can't borrow the node role. **Workload security:** Pod Security Admission `restricted` on tenant namespaces; Kyverno/Gatekeeper policies to enforce approved registries, signed images, required labels, and no `hostPath`/host networking. **Network:** default-deny NetworkPolicies per namespace (VPC CNI network policy, or Cilium/Calico), plus Security Groups for Pods where tenants need different access to AWS resources such as RDS. **Compute isolation:** for tenants that need stronger separation, dedicated Karpenter NodePools/managed node groups with tenant taints + node affinity (no kernel sharing with other tenants); Fargate gives per-Pod VM isolation for the highest-risk ones. **Quotas & fairness:** `ResourceQuota` (CPU, memory, Pod count, LoadBalancers, PVCs/storage) and `LimitRange` defaults per namespace, and restrict which PriorityClasses tenants may use so nobody can preempt others. **Observability & cost:** a `tenant` label on everything; metrics into Amazon Managed Prometheus / Mimir with per-tenant isolation, logs into Loki tenants or per-tenant CloudWatch log groups via Fluent Bit, Grafana orgs/folders with RBAC per tenant, and per-tenant cost via Kubecost or EKS split cost allocation data. If a tenant needs cluster-admin-like control (CRDs, operators), give them a **vCluster** or a separate cluster — namespaces can't safely provide that.

### 56. The kubelet keeps restarting on one particular node. How do you isolate the issue and keep the node stable?
First protect workloads: `kubectl cordon` the node (and `drain` if it's flapping `NotReady`) so nothing new lands there while you investigate. Then read why it dies: `systemctl status kubelet` and `journalctl -u kubelet -b --no-pager | tail -200` — the last lines before each exit usually name the cause. Common ones: **container runtime unavailable** (containerd down or its socket path wrong — check `systemctl status containerd`, `crictl info`); **cgroup driver mismatch** between kubelet and containerd (both should be `systemd` on modern distros); **expired/invalid kubelet client certificate** or failed cert rotation (`/var/lib/kubelet/pki`, plus clock skew — check NTP/chrony); **bad config** after a change (`/var/lib/kubelet/config.yaml`, kubelet flags, or on EKS the bootstrap/user-data); **disk full** on `/var/lib/kubelet` or `/var/lib/containerd` (`df -h`, `df -i` for inodes); **the kubelet itself getting OOM-killed** because nothing is reserved for system daemons (`dmesg -T | grep -i oom`); and version skew if this node was upgraded differently from the rest. Compare against a healthy node in the same group (same AMI? same kernel? same config?) — a difference usually points straight at the cause. For stability: set `kubeReserved`/`systemReserved` and sensible `evictionHard` thresholds so workloads can't starve the kubelet; run node-problem-detector and alert on kubelet restarts/NotReady flapping; and in cloud environments treat nodes as cattle — once you've captured the evidence, terminate the node and let the node group/Karpenter replace it, then fix the root cause in the AMI or launch template so it doesn't recur.

### 57. A critical production Pod gets evicted due to node pressure. How do you prevent it from happening again, and how do QoS classes play a role?
When a node hits a pressure threshold (memory, disk/ephemeral storage, PIDs), the kubelet evicts Pods to recover. It ranks candidates by: whether the Pod's usage **exceeds its requests**, then **Pod priority**, then usage relative to requests. That's where QoS (Q29) matters: **BestEffort** (no requests/limits) always exceeds its zero request, so it goes first; **Burstable** Pods using more than they requested go next; **Guaranteed** Pods (requests == limits for every container, CPU and memory) are almost never over their requests, so they're last — and they also get the lowest OOM score, so the kernel OOM killer picks them last too. To protect the critical Pod: make it **Guaranteed** with requests sized from real usage (VPA in recommendation mode helps); give it a high **PriorityClass**, which also lets it preempt lower-priority Pods to get scheduled; set **ephemeral-storage requests/limits** and ship logs off-node, since disk pressure from runaway logs or `emptyDir` is a frequent hidden cause. Fix the node side too: reserve resources for the system (`kubeReserved`/`systemReserved`), tune eviction thresholds (soft eviction with a grace period before hard), and stop overcommitting nodes with BestEffort/heavily burstable neighbours (LimitRange defaults, ResourceQuota). For resilience, run multiple replicas with anti-affinity/topology spread so one eviction isn't an outage. Gotcha: a **PodDisruptionBudget does *not* protect against node-pressure eviction** — PDBs only gate API-initiated evictions such as `kubectl drain`; kubelet pressure eviction ignores them.

### 58. You need to deploy a service that uses both TCP and UDP on the same port. How do you configure this with Services and Ingress?
A Service can list the same port number twice with different protocols, as long as each entry has a unique `name`:
```yaml
apiVersion: v1
kind: Service
metadata: {name: dns}
spec:
  type: LoadBalancer        # also works for ClusterIP / NodePort
  selector: {app: dns}
  ports:
  - {name: dns-udp, port: 53, targetPort: 53, protocol: UDP}
  - {name: dns-tcp, port: 53, targetPort: 53, protocol: TCP}
```
For `ClusterIP`/`NodePort` this has always worked. For `type: LoadBalancer`, mixed protocols became GA in Kubernetes 1.26 (`MixedProtocolLBService`), but the **cloud load balancer must support it**: on AWS use the AWS Load Balancer Controller with an NLB (`service.beta.kubernetes.io/aws-load-balancer-type: external`), which creates a `TCP_UDP` listener; a Classic ELB can't do UDP at all. On older clusters or providers without support, create two LoadBalancer Services (one per protocol) and share the IP where the provider allows it (e.g. MetalLB's `allow-shared-ip` annotation). **Ingress can't do this**: the Ingress API is HTTP/HTTPS (L7) only. Options are ingress-nginx's `tcp-services`/`udp-services` ConfigMaps (exposes raw L4 ports through the controller's Service), or the Gateway API's `TCPRoute`/`UDPRoute` with a controller that supports them (Envoy Gateway, Cilium, Istio). For most production L4 traffic (DNS, SIP, game servers, syslog), a LoadBalancer Service backed by an NLB is the simplest and right answer. Also remember health checks: UDP can't be health-checked directly, so the NLB target group typically health-checks over TCP/HTTP.

### 59. An application upgrade caused downtime even though rolling updates were configured. What advanced strategies would you apply to ensure zero-downtime deployments next time?
A rolling update only guarantees Pods are replaced gradually — not that traffic moves gracefully. Usual root causes and fixes: **Bad readiness** — no readiness probe, or one that returns OK before caches/connections are ready, so traffic hits Pods that can't serve it; use a real readiness endpoint plus a `startupProbe` for slow starters, and `minReadySeconds` so a Pod must stay healthy for a while before it counts. **Termination race** — on deletion, endpoint removal (kube-proxy, ingress, cloud LB) happens *in parallel* with SIGTERM, so Pods die while still receiving traffic; add a `preStop` hook (`sleep 10–15`), handle SIGTERM by draining in-flight requests, and set `terminationGracePeriodSeconds` above preStop + drain time. On AWS ALB, enable **Pod readiness gates** in the AWS Load Balancer Controller and match the target group's deregistration delay. **Capacity during rollout** — use `maxUnavailable: 0`, `maxSurge: 25%` (or 1) so capacity never drops; HPA `minReplicas` sized for peak traffic; a **PodDisruptionBudget** so node drains/upgrades during the rollout don't take down too many at once. **Incompatible changes** — a DB migration or API change that the old and new versions can't both handle during the overlap; use expand/contract migrations and backward-compatible APIs so both versions can run side by side. **Long-lived connections** (WebSockets, gRPC) need client reconnect logic and server-side draining. Beyond that: **progressive delivery** with Argo Rollouts or Flagger — canary (1% → 10% → 50% → 100%) with automated analysis against error-rate/latency SLOs and automatic rollback, or **blue-green** with instant switchback; decouple deploy from release with **feature flags**; set `progressDeadlineSeconds` so stuck rollouts fail loudly; and run the same rollout against staging under synthetic load first. Then write a short post-incident review so the specific failure becomes a pipeline check, not tribal knowledge.

### 60. A Pod is not running. How would you troubleshoot it?
Start with `kubectl get pod <pod> -o wide` and read the **STATUS** column, because each state points to a different layer. Then run `kubectl describe pod <pod>` (the **Events** section at the bottom is usually where the answer is) and `kubectl logs <pod> [-c container] [--previous]`.

| Status | What it means | Where to look |
|---|---|---|
| **Pending** | The scheduler can't place it | Events: `Insufficient cpu/memory` (requests too big, or the cluster is full → autoscaler), node taints/affinity/nodeSelector mismatch, PVC not bound (`kubectl get pvc`), ResourceQuota exceeded |
| **ContainerCreating** (stuck) | Scheduled, but the node can't start it | Volume mount failures (missing Secret/ConfigMap, EBS attached to another AZ/node), CNI out of IPs, image still pulling |
| **ImagePullBackOff / ErrImagePull** | Can't fetch the image | Typo in image/tag, private registry without `imagePullSecrets`, registry rate limit, node has no egress |
| **CrashLoopBackOff** | Container starts, then exits repeatedly | `kubectl logs --previous` for the last crash. Exit code via `kubectl get pod -o jsonpath='{.status.containerStatuses[*].lastState}'`: `137` = OOMKilled/SIGKILL, `1` = app error, `127` = command not found. Also a liveness probe killing it, or a bad command/args/env/config |
| **Running but 0/1 Ready** | Readiness probe failing | Probe path/port wrong, app slow to start (add a `startupProbe`), a dependency (DB) unreachable. The Pod gets no Service traffic |
| **Init:0/1, Init:CrashLoopBackOff** | An init container is failing | `kubectl logs <pod> -c <init-container>` |
| **Evicted / OOMKilled / Error** | Killed by the node or kernel | `describe` shows the reason: memory/disk pressure on the node, or the memory limit exceeded |
| **Terminating** (stuck) | Finalizers, or the node is down | Check `metadata.finalizers` and the node status. `--force --grace-period=0` is the last resort |

Then widen the scope if the Pod itself looks fine: `kubectl get events -n <ns> --sort-by=.lastTimestamp`, `kubectl describe node <node>` (pressure conditions, allocatable vs allocated), `kubectl get deploy/rs` (a ReplicaSet that can't create Pods because of quota or admission webhook errors shows the error on the RS, not on any Pod), and `kubectl exec -it <pod> -- sh` or `kubectl debug` with an ephemeral container for network/DNS checks from inside. In interviews, say the order out loud: **status → describe/events → logs (current and previous) → node → controller → exec/debug**. It shows a method rather than guessing.

### 61. What happens when a container exceeds its CPU or memory limit?
They behave very differently because CPU is **compressible** and memory is **not**.

- **CPU over limit → throttled, never killed.** The limit becomes a CFS quota in the container's cgroup (e.g. `limits.cpu: 500m` = 50ms of CPU time per 100ms period). Once the container uses its quota, its threads are paused until the next period. Symptoms: higher latency and timeouts, and failing liveness probes, which can then *indirectly* cause restarts. You see it in the `container_cpu_cfs_throttled_periods_total` metric. Multi-threaded apps (JVM, Go with many goroutines) can use the quota in a few ms and stall for the rest of the period, even at low average CPU. That's why many teams set CPU **requests** but leave out CPU **limits** for latency-sensitive services.
- **Memory over limit → OOMKilled.** The kernel OOM killer in the cgroup kills the process right away (SIGKILL, so no graceful shutdown). The container shows `Reason: OOMKilled`, exit code **137**, and the kubelet restarts it per `restartPolicy`. Repeated kills lead to CrashLoopBackOff. Fix it by finding a leak or raising the limit, and by making runtimes respect cgroup limits (JVM `-XX:MaxRAMPercentage`, Node `--max-old-space-size`).
- **Different thing, often confused: node-level pressure eviction.** If the whole *node* runs low on memory/disk/PIDs, the kubelet **evicts** Pods (status `Evicted`), even ones under their own limits. It starts with Pods using the most above their requests, so BestEffort before Burstable before Guaranteed (QoS). Ephemeral-storage over its limit also causes eviction.
- **Requests vs limits link**: requests drive scheduling and eviction order. Limits drive throttling and OOM kills. Memory request = limit (Guaranteed QoS) is the usual setting for critical Pods.

### 62. A user is unable to access an application exposed through a NodePort service. How would you troubleshoot it?
Follow the packet path, **client → node IP:NodePort → kube-proxy rules → Service → endpoints → Pod port**, and check each hop from the inside out:

1. **Is the Pod itself healthy?** `kubectl get pods -l app=myapp -o wide`. It must be `Running` **and** `Ready` (1/1). A Pod failing its readiness probe is removed from the endpoints, so the Service silently has nowhere to send traffic.
2. **Does the Service actually select the Pods?** `kubectl get endpoints myapp-svc` (or `kubectl get endpointslices -l kubernetes.io/service-name=myapp-svc`). **Empty endpoints** is the #1 cause: the Service `selector` doesn't match the Pod labels (typo, different `app:` value) or the namespace is wrong.
3. **Are the ports wired correctly?** `kubectl describe svc myapp-svc`: `port` (Service port), `targetPort` (**must equal the port the container actually listens on**), and `nodePort` (30000–32767). Test from inside the cluster: `kubectl run tmp --rm -it --image=busybox -- wget -qO- http://myapp-svc:<port>`. If that works, the problem is outside the cluster. If not, it's the Service/Pod.
4. **Is the app listening on the right interface?** An app bound to `127.0.0.1` inside the container is unreachable from outside the Pod. It must listen on `0.0.0.0`. Check with `kubectl exec -it <pod> -- netstat -tlnp` (or `ss -tlnp`) and `kubectl port-forward pod/<pod> 8080:<port>`.
5. **Can you hit the NodePort from the node itself?** `curl http://<node-internal-ip>:<nodePort>` from a node or a host in the VPC. If that works but the user can't reach it, the issue is the network in between.
6. **Firewall / cloud security groups**: NodePorts need the **node's security group / firewall to allow inbound 30000–32767** (or that specific port) from the user's source IP. Also check host firewalls (`iptables`/`firewalld`/`ufw`) and NACLs.
7. **Right IP?** The user needs a **node's reachable IP** (the public IP if they're outside the VPC). Nodes in private subnets have no public IP, so NodePort won't work from the internet. That's what `LoadBalancer`/Ingress is for.
8. **`externalTrafficPolicy: Local`?** Then only nodes that **run a Pod of that Service** answer on the NodePort. Hitting a node without a local Pod fails (by design, to preserve client IP).
9. **kube-proxy / CNI health**: `kubectl -n kube-system get pods | grep -E 'kube-proxy|calico|cilium|aws-node'`, and on the node `iptables-save | grep <nodePort>` (or `ipvsadm -Ln`). **NetworkPolicies** that deny ingress to the Pod also block NodePort traffic.

Interview summary: **"Pod Ready → endpoints not empty → targetPort matches container port → app listens on 0.0.0.0 → curl the NodePort from a node → open the security group/firewall → right node IP → externalTrafficPolicy → kube-proxy/NetworkPolicy."**

### 63. What is affinity, and what is node affinity in Kubernetes?
**Affinity** is a set of scheduling rules that tells the scheduler **where a Pod should (or must) run**, based on labels. There are three kinds:

| Type | Based on | Use case |
|---|---|---|
| **Node affinity** | Labels on **nodes** | "Run on SSD nodes / in zone us-east-1a / on GPU instances" |
| **Pod affinity** | Labels on **other Pods** already running | "Put my cache next to my app (same node/zone) for low latency" |
| **Pod anti-affinity** | Labels on other Pods | "Spread my replicas across nodes/zones so one failure doesn't take them all down" |

Each comes in two strengths:
- `requiredDuringSchedulingIgnoredDuringExecution`: a **hard** rule. If no node matches, the Pod stays **Pending**.
- `preferredDuringSchedulingIgnoredDuringExecution`: a **soft** rule with a `weight` (1–100). The scheduler tries, but schedules anyway if it can't.
- "IgnoredDuringExecution" means that if node labels change later, already-running Pods are **not** evicted.

**Node affinity** is the more expressive replacement for `nodeSelector`: it supports operators `In`, `NotIn`, `Exists`, `DoesNotExist`, `Gt`, `Lt`, and OR across terms.
```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: node.kubernetes.io/instance-type
                operator: In
                values: ["m6i.large", "m6i.xlarge"]
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 80
          preference:
            matchExpressions:
              - key: topology.kubernetes.io/zone
                operator: In
                values: ["us-east-1a"]
    podAntiAffinity:                       # spread replicas, one per node
      requiredDuringSchedulingIgnoredDuringExecution:
        - labelSelector:
            matchLabels: { app: web }
          topologyKey: kubernetes.io/hostname   # "same node" = same domain; use topology.kubernetes.io/zone for zones
```
**How it relates to taints/tolerations** (Q31): affinity **attracts** a Pod to nodes, while taints **repel** Pods from nodes. To dedicate nodes to a workload you need both: taint the nodes so others stay off, and add a toleration plus node affinity so your Pods go there. For simply spreading replicas evenly, `topologySpreadConstraints` is often simpler than pod anti-affinity and scales better in big clusters.
