# Secrets Management (Runtime / Infrastructure)

Dedicated secrets managers vs plain env vars, HashiCorp Vault core concepts and dynamic secrets, Kubernetes-native Secret limitations, and a worked example of fetching a secret at runtime. This file covers **runtime/infrastructure** secrets — for CI-pipeline-specific secrets handling (GitHub Actions secrets scoping, OIDC), see [GitHub Actions secrets-and-security.md](../Continuous%20Integration/GithubActions/secrets-and-security.md).

## 1. Why Dedicated Secrets Managers Beat Plain Env Vars / Config Files

The naive approach — a database password in an `.env` file or a plain environment variable — works functionally, but has structural weaknesses a dedicated secrets manager (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault, GCP Secret Manager) is specifically built to address:

| Concern | Plain env var / config file | Dedicated secrets manager |
|---|---|---|
| Rotation | Manual — someone has to edit the file/var and redeploy everywhere it's used | Often automatic; consumers fetch the current value, no redeploy needed |
| Audit logging | None — no record of who/what read the secret, or when | Every read is logged: identity, timestamp, secret path |
| Access control granularity | Whoever can read the file/env can read the secret — usually coarse (the whole Pod/host) | Fine-grained policy per secret path, per identity |
| Lifetime | Static — same value until someone manually changes it | Supports dynamic, short-lived credentials (§2) that expire automatically |
| Blast radius on leak | The full static value, valid until manually rotated | Often a short-lived lease that expires on its own, shrinking the exploitable window |
| Versioning / rollback | Usually none — overwritten value is just gone | Most managers keep version history |

The gap widens further with **dynamic secrets** (§2) — a plain env var is fundamentally incapable of being "generated fresh per consumer with a built-in expiry," while that's a first-class feature of Vault and the cloud-native equivalents.

## 2. HashiCorp Vault Core Concepts

### Secret engines

Vault organizes secrets access through pluggable **secret engines**, each handling a different backend/use case:

| Engine | Purpose |
|---|---|
| `kv` (key-value) | Static secret storage — closest to "a secure version of a config file" |
| `database` | Generates **dynamic**, short-lived database credentials on demand |
| `pki` | Issues short-lived TLS certificates |
| `aws` / `gcp` / `azure` | Generates short-lived cloud IAM credentials on demand |
| `transit` | Encryption-as-a-service — encrypt/decrypt data without Vault ever storing the plaintext |

### Dynamic secrets — the core differentiator

A **static** secret (a `kv` entry) is just a stored value someone put there — Vault didn't generate it, doesn't know if it's still valid elsewhere, and can't revoke it at the source.

A **dynamic** secret is generated by Vault **on demand**, tied to the actual backend system, with a built-in lease:

```bash
# Configure the database secrets engine once (admin/setup step)
vault secrets enable database
vault write database/config/my-postgres \
  plugin_name=postgresql-database-plugin \
  connection_url="postgresql://{{username}}:{{password}}@db.internal:5432/appdb" \
  allowed_roles="readonly-role"

vault write database/roles/readonly-role \
  db_name=my-postgres \
  creation_statements="CREATE ROLE \"{{name}}\" WITH LOGIN PASSWORD '{{password}}' VALID UNTIL '{{expiration}}'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO \"{{name}}\";" \
  default_ttl="1h" \
  max_ttl="24h"

# An application (or a human) requests a credential — Vault creates a REAL, brand-new
# database role at request time, with a password nobody else has ever seen
vault read database/creds/readonly-role
```

```
Key             Value
---             -----
lease_id        database/creds/readonly-role/abcd1234
lease_duration  1h
username        v-readonly-role-a1b2c3d4e5f6
password        A1a-generated-random-password
```

This credential:
- **Is unique** — created fresh for this specific request, not shared across every consumer.
- **Expires automatically** after `default_ttl` (renewable up to `max_ttl` via `vault lease renew <lease_id>`).
- **Can be revoked immediately** (`vault lease revoke <lease_id>`), which for the database engine means Vault actually `DROP ROLE`s it — the credential stops working everywhere at once, not just "stops being handed out."

Compare to a static shared DB password: if it leaks, it's valid indefinitely until someone manually rotates it *and* updates every consumer — a slow, error-prone, all-hands operation. A dynamic credential that leaks is valid for, at most, its remaining lease — often minutes to hours — and revoking it doesn't require touching every consumer, just the one lease.

### Leases and renewal

Every dynamic secret (and many static ones read via certain engines) comes with a **lease** — Vault's tracked record of "this value is valid until X, renewable up to Y." Well-behaved clients renew leases proactively before expiry rather than waiting for a hard failure; Vault client libraries typically handle this automatically.

## 3. Kubernetes-Native Secrets — Real Limitations

Kubernetes ships a built-in `Secret` object, which looks like the right tool but has meaningful gaps:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  password: c3VwZXJzZWNyZXQ=   # base64-encoded — NOT encrypted
```

### Base64 is not encryption

`data` fields in a `Secret` are **base64-encoded, not encrypted**. Anyone with `get`/`list` RBAC access to Secrets in that namespace — or read access to the underlying etcd data if it isn't encrypted at rest (next point) — can trivially decode the value:

```bash
kubectl get secret db-credentials -o jsonpath='{.data.password}' | base64 -d
# supersecret
```

Base64 exists to let arbitrary binary data survive YAML/JSON transport, not to provide confidentiality. Treating it as "the secret is protected" is a common and dangerous misunderstanding.

### etcd encryption at rest

By default, Kubernetes `Secret` objects are stored in **etcd in plaintext** (base64-encoded, which as above is not real protection) unless the cluster explicitly has **encryption at rest** configured:

```yaml
# EncryptionConfiguration — applied to the API server, encrypts Secret data before it hits etcd
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources: ["secrets"]
    providers:
      - aescbc:
          keys:
            - name: key1
              secret: <base64-encoded-32-byte-key>
      - identity: {}   # fallback for reading pre-existing unencrypted secrets during migration
```

Without this, anyone who gains read access to etcd directly (a backup, a snapshot, a misconfigured etcd endpoint) reads every Secret in the cluster in the clear. Most managed Kubernetes offerings (EKS, GKE, AKS) offer this as a checkbox/config option — verify it's actually enabled, don't assume it's on by default.

### The more secure alternative: external-secrets-operator or direct Vault integration

Rather than storing the actual secret value in Kubernetes at all, sync it in from an external, purpose-built secrets manager:

```yaml
# external-secrets-operator: Kubernetes never stores the real secret long-term —
# it's synced from Vault/AWS Secrets Manager/etc. and can be re-synced or revoked at the source
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: db-credentials
spec:
  refreshInterval: 1h              # re-pull from the source periodically, picking up rotations
  secretStoreRef:
    name: vault-backend
    kind: SecretStore
  target:
    name: db-credentials            # the operator creates/updates a normal K8s Secret FROM this source
  data:
    - secretKey: password
      remoteRef:
        key: secret/data/my-postgres
        property: password
```

This keeps the source of truth in Vault (or a cloud secrets manager) — the Kubernetes-side `Secret` becomes a synced, refreshable copy rather than the system of record, and rotation at the source propagates automatically on the next refresh interval instead of requiring a manual `kubectl` update everywhere the secret is consumed.

## 4. Worked Example: Fetching a Secret at Runtime Instead of Baking It Into an Env Var

**Anti-pattern**: secret baked into the Deployment spec as a static env var.

```yaml
# ANTI-PATTERN — visible via `kubectl describe pod`, /proc/<pid>/environ, crash dumps,
# and anyone with RBAC read access to Pods, not just Secrets
env:
  - name: DB_PASSWORD
    value: "supersecret123"
```

**Better pattern**: application authenticates to Vault at startup and fetches a short-lived credential itself, so the value never sits in a Pod spec or a static Secret at all.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  annotations:
    vault.hashicorp.com/agent-inject: "true"          # Vault Agent sidecar injects secrets as files
    vault.hashicorp.com/role: "my-app"
    vault.hashicorp.com/agent-inject-secret-db-creds: "database/creds/readonly-role"
spec:
  serviceAccountName: my-app        # Vault authenticates this Pod via its Kubernetes ServiceAccount token
                                      # (Vault's Kubernetes auth method) — no static Vault token stored anywhere
  containers:
    - name: app
      image: myregistry/myapp:1.4.0
      # app reads its DB credential from the file the Vault Agent sidecar writes,
      # e.g. /vault/secrets/db-creds — refreshed automatically as the lease is renewed
```

```python
# application code — read the freshly-issued credential from the injected file,
# not from an env var baked in at deploy time
with open("/vault/secrets/db-creds") as f:
    creds = parse_vault_secret_file(f.read())
conn = connect(user=creds["username"], password=creds["password"])
```

The authentication chain here mirrors [iam-and-least-privilege.md §4](iam-and-least-privilege.md) exactly: the Pod's Kubernetes ServiceAccount identity (already short-lived, already platform-issued) is the thing that's trusted — there's no static Vault token or database password stored in the cluster at all, only a chain of short-lived, automatically-renewed credentials from identity token → Vault lease → database role.
