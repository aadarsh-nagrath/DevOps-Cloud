## Junior Level (0–2 yrs)

### 1. What is Kubernetes, and what problem does it solve?
Kubernetes (K8s) is an open-source container orchestration platform that automates deploying, scaling, healing, and networking containerized applications across a cluster of machines. It solves the operational problems that appear once you have more than a handful of containers: scheduling them onto available capacity, restarting them when they crash, rolling out updates without downtime, load-balancing traffic across replicas, and managing configuration/secrets — all declaratively instead of via manual scripts.

### 2. What is the difference between a Pod, a container, and a node?
A **container** is a single running application process (as covered in the Docker section). A **Pod** is Kubernetes' smallest deployable unit — a group of one or more containers that share the same network namespace (same IP, `localhost` between them) and can share storage volumes; most Pods run exactly one container, with multiple only for tightly-coupled sidecar patterns. A **node** is a physical or virtual machine (worker) in the cluster that actually runs Pods, managed by the control plane.

### 3. What is the Kubernetes control plane, and what are its main components?
The control plane is the cluster's "brain," making global decisions and reacting to cluster state. Key components: **kube-apiserver** (the front door — all interaction, including `kubectl`, goes through its REST API), **etcd** (the distributed key-value store holding all cluster state), **kube-scheduler** (decides which node a new Pod should run on), and **kube-controller-manager** (runs the control loops — Deployment controller, Node controller, etc. — that continuously reconcile actual state toward desired state).

### 4. What runs on a worker node?
**kubelet** (the agent that talks to the API server and ensures containers described in assigned PodSpecs are actually running, reporting node/pod status back), **kube-proxy** (maintains network rules on the node so Services can route traffic to the right Pods), and the **container runtime** (containerd or CRI-O, implementing the Container Runtime Interface that actually pulls images and runs containers).

### 5. What is a Deployment, and how is it different from directly creating a Pod?
A Deployment is a higher-level object that manages a ReplicaSet, which in turn manages a set of identical Pod replicas — declaratively describing "I want N copies of this Pod spec running, always." If you create a bare Pod directly and it crashes or its node dies, nothing recreates it. A Deployment continuously reconciles: if a Pod dies, the ReplicaSet notices the actual count is below desired and creates a replacement; Deployments also manage rolling updates and rollbacks, which bare Pods/ReplicaSets don't handle on their own.

### 6. What is a Service, and why do Pods need one instead of just using Pod IPs directly?
Pod IPs are ephemeral — a Pod gets a new IP every time it's recreated (crash, rescheduling, rolling update). A **Service** provides a stable virtual IP and DNS name that automatically load-balances traffic across whichever Pods currently match its label selector, regardless of Pod churn — so other workloads can reliably reach "the backend service" without tracking individual Pod IPs themselves.

### 7. What are the main Service types (`ClusterIP`, `NodePort`, `LoadBalancer`, `ExternalName`)?
`ClusterIP` (the default) exposes the Service only inside the cluster, on an internal virtual IP. `NodePort` additionally exposes it on a static port on every node's IP, reachable from outside the cluster. `LoadBalancer` provisions an external cloud load balancer (AWS ELB/NLB, GCP LB, etc.) that routes to the Service — the standard way to expose a Service to the internet on a cloud provider. `ExternalName` maps the Service to an external DNS name (a CNAME), with no proxying involved at all — useful for referencing an external database or API by an internal, cluster-consistent name.

### 8. What is a namespace in Kubernetes, and why use multiple namespaces?
A namespace is a virtual, logical partition within a single physical cluster, scoping names (two objects can share a name if they're in different namespaces) and often used as a boundary for RBAC permissions, resource quotas, and network policies. Common patterns: one namespace per environment (`dev`, `staging`, `prod`) or per team/application — though note namespaces are *not* a strong security boundary on their own (Pods across namespaces can reach each other over the network by default unless NetworkPolicies restrict it).

### 9. What is a ConfigMap, and how is it different from a Secret?
Both decouple configuration from container images, injectable into Pods as environment variables or mounted files. A **ConfigMap** holds non-sensitive configuration (feature flags, config file contents, URLs). A **Secret** holds sensitive data (passwords, tokens, TLS certs) — stored base64-*encoded* (not encrypted) by default in `etcd`, so a Secret is not meaningfully more "secure" than a ConfigMap unless you separately enable encryption-at-rest for `etcd` and tightly control RBAC access to Secrets.

### 10. What is a Label and a Selector, and how do they relate?
A **label** is an arbitrary key-value pair attached to an object (`app: frontend`, `env: prod`) for identification/organization. A **selector** is a query against those labels (`app=frontend`) used by Services, Deployments, and other controllers to determine which set of objects they should act on — this loose, label-based coupling (rather than direct references) is a core Kubernetes design principle, letting you regroup/retarget objects just by changing labels.

### 11. What's the difference between `kubectl apply` and `kubectl create`?
`kubectl create` imperatively creates a new object from a manifest and fails if it already exists. `kubectl apply` is declarative — it creates the object if it doesn't exist, or computes and applies a diff/patch against the live object if it does, making it safe to re-run repeatedly (idempotent), which is why `apply` is the standard command for GitOps/CI-driven deployments rather than `create`.

### 12. What does `kubectl get pods`, `kubectl describe pod`, and `kubectl logs` each tell you, and when do you reach for each?
`kubectl get pods` gives a quick, high-level status list (name, ready count, status, restarts, age) — your first look at "is anything obviously wrong." `kubectl describe pod <name>` gives full details plus, critically, the **Events** section at the bottom, showing scheduling decisions, image pull issues, and probe failures — the first place to look when a Pod won't start. `kubectl logs <pod> [-c container] [-f] [--previous]` shows the container's stdout/stderr — `--previous` is essential for a crash-looping container, since it shows the logs from the *last* (crashed) instance rather than the fresh, empty logs of the just-restarted one.

### 13. What is a ReplicaSet?
A ReplicaSet ensures a specified number of identical Pod replicas (matching a label selector) are running at any given time, creating or deleting Pods as needed to reconcile actual vs. desired count. In practice you rarely create ReplicaSets directly — you create a Deployment, which creates and manages ReplicaSets for you (one per revision, enabling rolling updates and rollback).

### 14. What is a rolling update, and how does a Deployment perform one?
A rolling update replaces Pods running the old version with the new version incrementally, rather than all at once, avoiding downtime. The Deployment creates a *new* ReplicaSet for the new version and gradually scales it up while scaling the old ReplicaSet down, governed by `maxSurge` (how many extra Pods above desired count are allowed during the rollout) and `maxUnavailable` (how many Pods can be unavailable at once) — `kubectl rollout status deployment/<name>` tracks progress, and `kubectl rollout undo deployment/<name>` rolls back to the previous ReplicaSet's spec if something goes wrong.

### 15. What are readiness probes and liveness probes, and how are they different?
A **liveness probe** answers "is this container still healthy, or should it be restarted?" — a failing liveness probe causes `kubelet` to kill and restart the container. A **readiness probe** answers "is this container ready to receive traffic right now?" — a failing readiness probe removes the Pod from a Service's load-balancing pool *without* restarting it (useful during slow startup, or temporary overload, where restarting wouldn't help and would only make things worse). Both can be defined via `httpGet`, `tcpSocket`, `exec`, or (since 1.23+ GA) `grpc` checks.

### 16. What happens when you delete a Pod that's managed by a Deployment?
The Deployment's ReplicaSet controller notices the actual replica count dropped below the desired count and immediately creates a new Pod to replace it — you can't "permanently" delete one Pod out of a Deployment this way, since the controller's whole job is to keep reconciling toward the desired count. To actually reduce the count, you scale the Deployment down (`kubectl scale deployment/<name> --replicas=2`) or delete the Deployment itself.

### 17. What is `kubectl port-forward`, and when would you use it?
`kubectl port-forward pod/<name> 8080:80` (or against a Service/Deployment) tunnels a local port on your machine directly to a port inside a specific Pod, without needing a Service, Ingress, or any cluster-external exposure — extremely useful for quickly debugging a Pod (hitting its API/metrics endpoint, connecting to a database Pod) from your laptop without changing any cluster configuration.

### 18. What is a StatefulSet, and how is it different from a Deployment?
A Deployment treats Pods as interchangeable — any replica can be replaced by any other, with no stable identity. A **StatefulSet** is for workloads needing stable, unique network identity and/or stable storage per replica (databases, message queues) — each Pod gets a predictable, persistent name (`web-0`, `web-1`, `web-2`, not random suffixes), is created/scaled/deleted in strict order, and (typically paired with `volumeClaimTemplates`) each replica keeps its *own* persistent volume across restarts/rescheduling, rather than sharing one or getting a fresh one.

### 19. What is a DaemonSet, used for what kind of workload?
A DaemonSet ensures exactly one copy of a Pod runs on every node (or a filtered subset of nodes) in the cluster, automatically adding a Pod when a new node joins. Typical use cases: log collection agents (Fluentd/Fluent Bit), node-level monitoring agents (node-exporter), and CNI/networking components that must run on every node by nature.

### 20. What is a Job and a CronJob?
A **Job** creates one or more Pods and ensures a specified number of them run to *successful completion* (unlike a Deployment, which keeps Pods running indefinitely) — used for batch/one-off tasks like a database migration. A **CronJob** creates Jobs on a recurring schedule using standard cron syntax (`0 2 * * *`) — used for scheduled batch work like nightly reports or backups.

## Mid Level (2–5 yrs)

### 21. Walk through exactly what happens from `kubectl apply -f pod.yaml` to the container actually running.
`kubectl` sends the manifest as a request to the **kube-apiserver**, which authenticates/authorizes it, runs it through admission controllers (validating/mutating webhooks), and persists the desired object into **etcd**. The **scheduler**, watching for unscheduled Pods, evaluates node capacity/affinity/taints and binds the Pod to a specific node by updating its `spec.nodeName`. The **kubelet** on that node, watching the API server for Pods assigned to it, sees the new binding and instructs the **container runtime** (via the CRI) to pull the image and start the container(s), then continuously reports the Pod's actual status back to the API server, which is what `kubectl get pods` reflects.

### 22. Explain the Kubernetes networking model — what must be true about Pod-to-Pod communication cluster-wide?
The fundamental requirement (enforced by whatever CNI plugin is installed, not by Kubernetes core itself): every Pod gets its own unique IP, and every Pod can reach every other Pod's IP directly, cluster-wide, *without NAT* — regardless of which node either is on. This "flat network" model is what lets application code treat Pod communication uniformly, without needing to know or care about node topology. CNI plugins (Calico, Cilium, Flannel, AWS VPC CNI) each implement this requirement differently (overlay networks via VXLAN, BGP-based routing, or direct VPC-native IP assignment), which is exactly why the CNI is pluggable rather than baked into Kubernetes itself.

### 23. What is `kube-proxy`, and how does it actually route traffic to a Service's backend Pods?
`kube-proxy` runs on every node and watches the API server for Service/Endpoint changes, translating them into local packet-forwarding rules — historically via `iptables` DNAT rules (rewriting the Service's virtual IP to a randomly-selected backend Pod IP), and increasingly via `IPVS` mode (better performance at very high Service/endpoint counts) or eBPF-based dataplanes (e.g. when using Cilium in kube-proxy-replacement mode). Either way, this happens entirely at the packet-forwarding layer on each node — there's no separate proxy process actually in the data path for every request.

### 24. What is an Ingress, and how is it different from a Service of type `LoadBalancer`?
A `LoadBalancer` Service provisions one cloud load balancer *per Service*, operating at L4 (TCP/UDP) — fine for a handful of services, but expensive and unwieldy at scale (one cloud LB per service). An **Ingress** is an L7 (HTTP/HTTPS) routing object that lets a *single* entry point (backed by one Ingress Controller, e.g. NGINX, Traefik, or a cloud-native one like AWS Load Balancer Controller) route to many different Services based on hostname/path rules, and typically also handles TLS termination — the standard way to expose multiple HTTP services cost-effectively.

### 25. What's the difference between requests and limits in a Pod's resource spec, and why does it matter for scheduling and stability?
`resources.requests` is what the scheduler *guarantees* is reserved for the container when deciding which node to place it on (a node won't be chosen if it can't satisfy the sum of requests of everything already scheduled there). `resources.limits` is the hard ceiling the container is *not allowed to exceed* at runtime — exceeding a CPU limit results in throttling; exceeding a memory limit results in an OOM-kill of that container. Setting requests too low relative to actual usage causes node overcommitment and noisy-neighbor problems; setting limits too low causes throttling/OOMKills even when the node has spare capacity — right-sizing both from real usage data (e.g. via VPA recommendations or historical metrics) is a core ongoing operational task.

### 26. What are Quality of Service (QoS) classes in Kubernetes, and how are they determined?
Kubernetes assigns each Pod one of three QoS classes based on its requests/limits: **Guaranteed** (every container has requests == limits, for both CPU and memory — highest protection, last to be evicted under node pressure), **Burstable** (at least one container has requests set, but requests != limits — evicted before Guaranteed Pods), and **BestEffort** (no requests or limits set at all — first to be evicted under any resource pressure). This directly determines eviction order when a node runs low on resources, so it's a real design lever, not just a label.

### 27. What is a Horizontal Pod Autoscaler (HPA), and how is it different from a Vertical Pod Autoscaler (VPA) and Cluster Autoscaler?
**HPA** scales the *number of Pod replicas* up/down based on observed metrics (CPU/memory utilization by default, or custom/external metrics via the metrics API) against a target Deployment/StatefulSet. **VPA** instead adjusts the *resource requests/limits* of existing Pods (recommending or automatically applying new values) rather than changing replica count — useful for right-sizing single-instance or hard-to-horizontally-scale workloads. **Cluster Autoscaler** operates one level up, adding or removing entire *nodes* from the cluster when Pods can't be scheduled due to insufficient capacity, or when nodes are underutilized — HPA/VPA and Cluster Autoscaler are complementary, commonly all three run together.

### 28. Explain taints and tolerations, and how they differ from node affinity.
A **taint** on a node (`kubectl taint nodes node1 key=value:NoSchedule`) repels Pods from scheduling there *unless* the Pod has a matching **toleration** — this is a node-driven mechanism ("I refuse most Pods unless they explicitly opt in," e.g. dedicating nodes to GPU workloads). **Node affinity** is the inverse direction — a Pod-driven mechanism expressing "I prefer/require nodes with these labels" — without an affinity rule, a Pod is happy to run anywhere that has no taint blocking it. Taints/tolerations and affinity are often combined: taint the special nodes *and* add matching tolerations plus affinity to the specific Pods that should land there, so ordinary Pods are both repelled (taint) and never even try to go there (no matching affinity needed, but the taint alone is often sufficient).

### 29. What is a PersistentVolume (PV) and a PersistentVolumeClaim (PVC), and how do they relate to StorageClasses?
A **PV** is a piece of actual storage in the cluster (an AWS EBS volume, an NFS share, etc.), provisioned either manually or dynamically. A **PVC** is a *request* for storage made by a user/Pod ("I need 10Gi, ReadWriteOnce") — Kubernetes binds a PVC to a matching PV. A **StorageClass** defines *how* to dynamically provision a PV when a PVC requests one (which provisioner/backend, what parameters like disk type/IOPS) — without dynamic provisioning via a StorageClass, an administrator would have to manually pre-create PVs to match every PVC, which doesn't scale operationally.

### 30. What is RBAC in Kubernetes, and what's the difference between a Role and a ClusterRole, and a RoleBinding and a ClusterRoleBinding?
RBAC (Role-Based Access Control) governs who can do what against the API server. A **Role** grants permissions (verbs like `get`/`list`/`create`/`delete` on resources like `pods`/`deployments`) scoped to a single namespace. A **ClusterRole** grants permissions cluster-wide, or against cluster-scoped resources (nodes, PVs) that have no namespace at all — it can also be *bound* within just one namespace via a RoleBinding, which is a common pattern for reusing a common permission set across many namespaces. A **RoleBinding** attaches a Role (or ClusterRole) to specific users/groups/ServiceAccounts within one namespace; a **ClusterRoleBinding** does the same cluster-wide.

### 31. What is a ServiceAccount, and how does a Pod use one to authenticate to the Kubernetes API?
A ServiceAccount is an identity for processes running *inside* the cluster (as opposed to human users, who authenticate differently). Every Pod is assigned a ServiceAccount (the namespace's `default` one, unless specified otherwise), and its credentials (a projected, automatically-rotated token since Kubernetes 1.22+, mounted at `/var/run/secrets/kubernetes.io/serviceaccount/`) are what any in-cluster code (like a controller or an app calling the K8s API) uses to authenticate — RBAC rules are then bound to that ServiceAccount to control exactly what it's permitted to do.

### 32. What's the difference between a NetworkPolicy's `ingress` and `egress` rules, and what happens if a namespace has zero NetworkPolicies?
`ingress` rules control what's allowed to connect *to* Pods matching the policy's selector; `egress` rules control what those Pods are allowed to connect *out to*. With **zero** NetworkPolicies applied to a Pod, the default is fully permissive — any Pod can talk to any other Pod, in any namespace, with no restriction at all (this surprises people who assume Kubernetes is "secure by default" on the network layer — it isn't, until you explicitly apply policies, and the CNI plugin must actually support NetworkPolicy enforcement in the first place, which not all of them do out of the box).

### 33. A Pod is stuck in `Pending` state. Walk through how you'd diagnose why.
`kubectl describe pod <name>` and read the **Events** section — this almost always states the reason directly: "Insufficient cpu/memory" (no node has enough allocatable resources left), "node(s) had taints that the pod didn't tolerate," "0/5 nodes are available: node affinity/selector didn't match," or a PVC that can't be bound (no matching PV or StorageClass provisioner issue). `Pending` specifically means the scheduler hasn't been able to bind the Pod to *any* node yet, so the investigation is almost always about node capacity, scheduling constraints, or unmet storage/networking prerequisites — not about the container itself (which hasn't even started).

### 34. A Pod is stuck in `CrashLoopBackOff`. Walk through how you'd diagnose why.
`CrashLoopBackOff` means the container *starts*, then exits (crashes), and Kubernetes is repeatedly restarting it with exponential backoff. `kubectl logs <pod> --previous` shows the crashed instance's actual output (the current attempt's logs are often empty since it just restarted) — the most common causes are an application error/misconfiguration causing immediate exit, a missing dependency (can't connect to a database at startup and the app doesn't retry, it just exits), a failing liveness probe repeatedly killing an otherwise-slow-to-start container, or (check `kubectl describe pod` for the exit code) an OOMKill (exit code 137) if it's a memory limit issue rather than an application logic issue.

### 35. What's the difference between `ImagePullBackOff` and `ErrImagePull`, and common root causes?
`ErrImagePull` is the immediate, first-attempt failure to pull an image; `ImagePullBackOff` is Kubernetes backing off and retrying after that initial failure. Common causes: a typo in the image name/tag, the image genuinely doesn't exist at that tag, missing or incorrect `imagePullSecrets` for a private registry, or (less obviously) the node's container runtime hitting a registry rate limit (a well-known issue with unauthenticated Docker Hub pulls at scale) — `kubectl describe pod` again shows the exact underlying error message from the runtime.

### 36. How do you perform a zero-downtime rolling restart of a Deployment without changing its image/config?
`kubectl rollout restart deployment/<name>` triggers a rolling replacement of all Pods (useful for picking up a changed ConfigMap/Secret that isn't automatically re-read by running Pods, or just cycling Pods for other operational reasons) using the same rolling-update mechanics (`maxSurge`/`maxUnavailable`) as a normal update — as long as readiness probes are correctly configured, traffic is never sent to a Pod before it's actually ready, giving a genuinely zero-downtime restart.

### 37. What's the difference between `emptyDir`, `hostPath`, and a PersistentVolume-backed volume?
`emptyDir` is ephemeral, Pod-lifetime-scoped scratch storage — created empty when the Pod starts, deleted permanently when the Pod is removed (useful for scratch space or sharing files between containers in the same Pod). `hostPath` mounts a path directly from the *node's* filesystem into the Pod — tightly couples the Pod to whichever specific node it lands on and is generally discouraged for application workloads (mostly used by system-level DaemonSets that genuinely need node filesystem access). A PV-backed volume (via a PVC) is durable, decoupled from any specific Pod or node, and is what you actually want for persistent application data.

## Senior Level (5+ yrs)

### 38. Explain the full Kubernetes reconciliation/controller pattern, and why "declarative, level-triggered" design is more robust than an imperative, event-triggered one.
Every controller runs a continuous loop: observe current state (via the API server, typically using informers/watches for efficiency rather than polling), compare it against desired state, and take action to reconcile any difference — repeated indefinitely, not just once in response to a single event. This "level-triggered" design (react to *current state*, not to *the specific event that changed it*) is robust because it self-heals from missed events, restarts, or race conditions — if a controller crashes and misses ten events, it doesn't matter, because on restart it just re-evaluates current-vs-desired state fresh and takes whatever action is still needed. An event-triggered ("edge-triggered") design, by contrast, would need every single transition event delivered reliably and processed in order, which is much harder to guarantee correctly at scale, especially across restarts and network partitions.

### 39. Design a multi-tenant Kubernetes cluster strategy for several internal teams with different trust levels. What isolation mechanisms would you layer, and where are the real boundaries?
Namespaces alone provide organizational/RBAC scoping but are not a strong isolation boundary — Pods across namespaces share the same kernel on shared nodes unless you do more. A real multi-tenant design layers: RBAC scoped tightly per-namespace per-team; ResourceQuotas and LimitRanges per namespace to prevent one tenant from starving others; NetworkPolicies (default-deny ingress/egress per namespace, explicit allow-lists) since Kubernetes networking is flat/open by default; PodSecurityStandards/admission control (restricted profile) to prevent privilege escalation, host namespace access, or privileged containers; and, for genuinely untrusted or higher-risk tenants, dedicating separate node pools (via taints/tolerations + node affinity) or even separate clusters entirely, since sharing a kernel via `runc` is fundamentally weaker isolation than a hypervisor boundary — the honest answer to "is namespace-based multi-tenancy secure" is "it raises the bar significantly but is not equivalent to hard tenant isolation," and the risk tolerance of the actual tenants should drive how far up that ladder (shared nodes → dedicated node pools → separate clusters → separate cloud accounts) you go.

### 40. Walk through diagnosing a cluster-wide issue where many unrelated Pods across the cluster start failing readiness probes simultaneously.
Given the "simultaneous, cluster-wide, unrelated workloads" pattern, suspect a shared-infrastructure cause rather than N independent application bugs: check `kube-apiserver` health/latency first (probes failing because the apiserver itself, or `etcd` behind it, is under load/unavailable can manifest as widespread probe timeouts if probes or their dependencies route through cluster DNS/API calls); check CoreDNS health and DNS resolution latency cluster-wide (a very common systemic cause — if application health checks or their dependencies rely on DNS and CoreDNS is degraded/overloaded, everything downstream looks broken simultaneously); check node-level resource pressure across the fleet (if many nodes are simultaneously CPU-throttled or under memory pressure, e.g. from a bad node-level DaemonSet rollout or a runaway cron job, probes cluster-wide can start timing out due to CPU starvation rather than any application-level fault); and check whether a recent cluster-level change correlates in time (a CNI upgrade, a node pool rotation, an admission webhook that started rejecting/delaying requests) rather than assuming it's coincidental that everything broke at once.

### 41. How does the Kubernetes scheduler actually decide where to place a Pod, in more depth than "it picks a node with capacity"?
Scheduling happens in two phases: **filtering** (find the set of nodes that satisfy hard constraints — sufficient resources, matching node selectors/affinity/taints-tolerations, volume topology constraints) and **scoring** (rank the filtered/feasible nodes using a set of weighted priority functions — spreading Pods across nodes/zones for availability, bin-packing to consolidate for efficiency, preferring nodes that already have the required image cached, honoring inter-pod affinity/anti-affinity preferences) and finally binds the Pod to the highest-scoring node. Custom scheduling needs (specialized bin-packing, GPU topology awareness, cost-aware placement) are handled via scheduler extenders, a custom scheduler plugin using the Scheduling Framework, or in some cases running an entirely separate custom scheduler for specific workload classes, selected per-Pod via `spec.schedulerName`.

### 42. Explain etcd's role in cluster reliability, and what an operator needs to know about it beyond "it's the database."
`etcd` is a distributed, Raft-consensus-based key-value store holding the entire cluster's state — every object, every status update, goes through it, making it the single most critical stateful component in a cluster (if `etcd` is lost with no backup, the cluster's control-plane state is unrecoverable even if all workload nodes are fine). Operationally: it requires low-latency, low-jitter disk I/O (SSD, ideally dedicated) since Raft consensus is latency-sensitive and a slow disk causes leader elections/instability under load; it should run as an odd-numbered cluster (3 or 5 members) for quorum tolerance; regular, tested (not just taken-and-forgotten) snapshots/backups are essential, since `etcd` corruption or majority member loss is one of the few Kubernetes failure modes with no automatic self-healing path; and its size/performance degrades with very large numbers of objects or excessive `watch` load, which is why very large clusters need explicit `etcd` capacity planning, not just node capacity planning.

### 43. What is the Container Storage Interface (CSI) and Container Network Interface (CNI), and why does this plugin architecture matter for how you evaluate a managed Kubernetes offering?
CSI and CNI are standardized interfaces that decouple Kubernetes core from any specific storage or networking implementation — any storage vendor/cloud can implement a CSI driver (AWS EBS CSI, Azure Disk CSI, Portworx) and any networking vendor can implement a CNI plugin (Calico, Cilium, AWS VPC CNI) without Kubernetes core needing to know about vendor specifics. This matters practically because "Kubernetes" behavior around networking (NetworkPolicy support, IP-per-Pod vs. overlay, performance) and storage (supported access modes, snapshot/resize capability, failure domains) varies significantly by *which* CNI/CSI a given managed offering defaults to or supports — so evaluating a managed Kubernetes service (EKS, GKE, AKS) or a specific cluster design genuinely requires looking one layer below "it's Kubernetes" into exactly which CNI/CSI implementation is in play and what it actually supports.

### 44. Design an upgrade strategy for a large, business-critical multi-cluster Kubernetes fleet, addressing version skew, testing, and rollback.
Maintain a documented, tested upgrade path following Kubernetes' supported version-skew policy (control plane can be up to a few minor versions ahead of kubelets, but not arbitrarily so) — never skip more minor versions than officially supported in one jump. Stage upgrades through environments (a canary/non-production cluster first, running real synthetic or shadow traffic, then a low-risk production cluster, then the rest) rather than upgrading every cluster simultaneously. Automate the control-plane and node-pool upgrade sequence (for managed offerings, this is largely provider-driven; for self-managed, tools like `kubeadm` plus careful node draining) with health verification gates between steps, and always read the release notes for deprecated/removed API versions *before* upgrading (a common real-world break: manifests still using an API version that was removed in the target release — `kubectl-convert` and `pluto`/`kube-no-trouble` help catch these ahead of time). Rollback for a control-plane upgrade is generally much harder than rollback for an application deployment (Kubernetes doesn't support downgrading the control plane cleanly in most cases), so the actual safety net is heavy pre-upgrade validation and canarying, not "roll back if it breaks."

### 45. How would you reason about and reduce the blast radius of a compromised Pod in a cluster you're responsible for securing?
Layer controls so a compromise of one Pod doesn't cascade: run as non-root with a read-only root filesystem and dropped capabilities (limits what the compromised process can even attempt); apply the `restricted` Pod Security Standard to prevent privilege escalation and host-namespace access in the first place; default-deny NetworkPolicies so a compromised Pod can't freely reach other Pods, the cloud metadata endpoint (a very common real-world pivot point to steal cloud IAM credentials — worth explicitly blocking `169.254.169.254` egress unless required), or the internet for exfiltration/C2; scope its ServiceAccount's RBAC permissions to the absolute minimum it needs (a compromised Pod with a ServiceAccount that can `list secrets` cluster-wide turns a single-Pod compromise into a cluster-wide credential leak); and ensure runtime detection (Falco or similar, watching for anomalous syscalls/process execution inside containers) is in place so a compromise that does occur is actually noticed rather than persisting silently — no single one of these is sufficient alone, which is the point of defense-in-depth.
