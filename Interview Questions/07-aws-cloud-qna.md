## Junior Level (0–2 yrs)

### 1. What is AWS, and what's the difference between IaaS, PaaS, and SaaS?
AWS (Amazon Web Services) is a cloud platform offering on-demand compute, storage, networking, and managed services over the internet, billed on usage. **IaaS** (Infrastructure as a Service, e.g. EC2) gives you raw virtualized infrastructure — you manage the OS and everything above it. **PaaS** (Platform as a Service, e.g. Elastic Beanstalk, App Runner) manages the OS/runtime for you — you just deploy code. **SaaS** (Software as a Service) is a complete, ready-to-use application (e.g. Gmail) where you manage nothing but your own data/configuration within it.

### 2. What is an AWS Region, an Availability Zone (AZ), and why does the distinction matter?
A **Region** is a geographically separate area (e.g. `us-east-1`, `ap-south-1`) containing multiple, physically isolated data centers. An **Availability Zone** is one of those isolated data centers (or clusters of them) within a region, connected to other AZs in the same region by low-latency links but with independent power/cooling/networking. Deploying across multiple AZs within a region protects against a single data center failure; deploying across multiple regions additionally protects against a regional-scale event and reduces latency for geographically distributed users.

### 3. What is EC2, and what are the main instance purchasing options?
EC2 (Elastic Compute Cloud) provides resizable virtual server instances. Purchasing options: **On-Demand** (pay per second/hour, no commitment, most expensive per unit but maximum flexibility), **Reserved Instances/Savings Plans** (commit to 1 or 3 years for a significant discount, for predictable steady-state workloads), and **Spot Instances** (bid on spare AWS capacity at up to ~90% discount, but can be reclaimed by AWS with only a short warning — suited to fault-tolerant, interruptible workloads like batch processing or stateless horizontally-scaled fleets, not for anything that can't tolerate sudden termination).

### 4. What is S3, and what are S3 storage classes for?
S3 (Simple Storage Service) is object storage — you store arbitrary files (objects) in buckets, addressed by key, with virtually unlimited scalability and 11 nines of durability. Storage classes let you trade cost against retrieval speed/frequency: **S3 Standard** (frequent access), **S3 Standard-IA**/**One Zone-IA** (infrequent access, cheaper storage but a retrieval fee), **S3 Glacier**/**Glacier Deep Archive** (long-term archival, cheapest storage, retrieval takes minutes to hours) — **S3 Intelligent-Tiering** automatically moves objects between tiers based on observed access patterns, removing the need to manually predict access frequency.

### 5. What is IAM, and what's the difference between an IAM user, a group, a role, and a policy?
IAM (Identity and Access Management) controls authentication and authorization in AWS. A **user** represents a specific person or application with long-lived credentials. A **group** is a collection of users sharing the same permissions, for easier management. A **role** is an identity *assumed temporarily* (by a user, an AWS service, or an external identity) rather than tied to permanent credentials — the recommended way to grant permissions to EC2 instances, Lambda functions, or cross-account access, since it avoids long-lived credentials entirely. A **policy** is a JSON document defining actual permissions (which actions on which resources are allowed/denied), attached to users, groups, or roles.

### 6. What is the AWS shared responsibility model?
AWS is responsible for the security **of** the cloud (physical data center security, the hardware, the hypervisor, managed service internals). The customer is responsible for security **in** the cloud (their data, IAM configuration, network/firewall rules, OS-level patching on unmanaged EC2 instances, encryption choices). Exactly where the line falls shifts depending on the service — for a fully-managed service like S3/Lambda, AWS handles more of the underlying stack; for raw EC2, the customer owns far more (guest OS patching, for instance).

### 7. What is a VPC, and what are subnets, public vs. private?
A VPC (Virtual Private Cloud) is your own logically isolated virtual network within AWS, where you define IP address ranges, subnets, route tables, and gateways. A **subnet** is a subdivision of the VPC's IP range, tied to a specific AZ. A subnet is "public" if its route table sends `0.0.0.0/0` traffic to an Internet Gateway (making resources in it directly internet-reachable, if also assigned a public IP), and "private" if it has no such route (or routes outbound-only traffic through a NAT Gateway) — the standard pattern is public subnets for load balancers/bastion hosts, private subnets for application servers and databases.

### 8. What's the difference between a Security Group and a Network ACL (NACL)?
A **Security Group** is a stateful virtual firewall attached to individual resources (EC2 instances, RDS instances) — if you allow inbound traffic on a port, the corresponding outbound response is automatically allowed regardless of outbound rules. A **NACL** is a stateless firewall applied at the *subnet* level — you must explicitly allow both inbound and outbound rules for traffic to flow in both directions, and rules are evaluated in numbered order. Security Groups are the primary, more commonly used control; NACLs are typically used as a coarser, secondary layer (e.g. explicitly blocking a known-bad IP range at the subnet level).

### 9. What is RDS, and why use it instead of running a database yourself on EC2?
RDS (Relational Database Service) is a managed relational database service (supporting MySQL, PostgreSQL, MariaDB, SQL Server, Oracle, and AWS's own Aurora) that handles provisioning, automated backups, patching, and (via Multi-AZ) automatic failover — removing most of the operational burden of running a database yourself, at the cost of somewhat less low-level control than a self-managed instance (e.g. no OS-level shell access, and Aurora aside, less flexibility around exotic extensions/configuration).

### 10. What is Lambda, and what does "serverless" actually mean?
Lambda runs your code in response to events (an API call, a file upload to S3, a scheduled trigger) without you provisioning or managing any server at all — you supply code and AWS handles execution environment, scaling (including down to zero when idle), and you're billed only for actual execution time/memory used. "Serverless" doesn't mean there are no servers — it means you, the developer, never provision, patch, or manage them; AWS abstracts that layer away entirely.

### 11. What is CloudWatch, and what's the difference between CloudWatch Metrics, Logs, and Alarms?
CloudWatch is AWS's native observability service. **Metrics** are numeric time-series data (CPU utilization, request count) collected automatically for most AWS services, and can be published as custom application metrics too. **Logs** collect and store log data (application logs, Lambda execution logs, VPC Flow Logs) and support querying via CloudWatch Logs Insights. **Alarms** watch a metric against a threshold and trigger an action (an SNS notification, an Auto Scaling action) when it's breached for a defined evaluation period.

### 12. What is an Elastic Load Balancer (ELB), and what are the different types (ALB, NLB, CLB)?
An ELB distributes incoming traffic across multiple targets (EC2 instances, containers, Lambda functions) for availability and scalability. **ALB** (Application Load Balancer) operates at L7 (HTTP/HTTPS), supporting path/host-based routing rules — the standard choice for web applications and microservices. **NLB** (Network Load Balancer) operates at L4 (TCP/UDP), handling extreme throughput/low-latency needs and static IPs, without inspecting HTTP content. **CLB** (Classic Load Balancer) is the legacy, older generation predating ALB/NLB, largely superseded and not recommended for new workloads.

## Mid Level (2–5 yrs)

### 13. Explain how IAM policy evaluation logic works — what happens when there are conflicting Allow and Deny statements across multiple attached policies?
AWS evaluates *all* applicable policies (identity-based policies on the user/role, resource-based policies on the resource itself, permissions boundaries, SCPs at the Organization level) together. The evaluation logic: an explicit **Deny** anywhere in any applicable policy always wins, overriding any Allow, no matter how many other policies grant access. If there's no explicit Deny, the request is allowed only if at least one applicable statement explicitly Allows it — by default, everything is implicitly denied unless something explicitly allows it (default-deny). This is why a single overly-broad `Deny` statement (or an SCP) can unexpectedly block access that individual IAM policies clearly seem to allow, and it's a very common real-world debugging scenario.

### 14. What is the principle of least privilege in AWS IAM, and what tools help you actually implement it (rather than just aspire to it)?
Least privilege means granting only the specific permissions an identity actually needs, nothing more — avoiding broad wildcard permissions (`"Action": "*"`) "to be safe/save time," which in practice just maximizes blast radius if that identity's credentials are ever compromised. Concrete tools: **IAM Access Analyzer** (identifies unused permissions and generates a least-privilege policy based on actual observed CloudTrail activity), **permissions boundaries** (a ceiling that caps the maximum permissions a role/user can ever have, even if a broader identity policy is later attached), and simply starting from AWS-managed policies scoped to a specific service/use case rather than `AdministratorAccess`, then narrowing further based on Access Analyzer findings over time.

### 15. What's the difference between a NAT Gateway and an Internet Gateway, and why can't a private subnet just use an Internet Gateway directly?
An **Internet Gateway** enables *bidirectional* internet connectivity — resources with a public IP in a subnet routed to it can both initiate and receive connections from the internet. A **NAT Gateway** enables *outbound-only* internet access for resources in a private subnet (e.g. so a private EC2 instance can download OS updates or call an external API) while remaining completely unreachable from the internet inbound — it works by translating the private instance's outbound traffic to use the NAT Gateway's own public IP, so return traffic comes back through it rather than the private instance ever being directly addressable from outside.

### 16. What's the difference between EBS, EFS, and S3, and when would you use each?
**EBS** (Elastic Block Store) is block storage attachable to exactly one EC2 instance at a time (like a virtual hard drive) — used for a VM's root/data volumes needing low-latency block-level access. **EFS** (Elastic File System) is a fully-managed, POSIX-compliant network file system that can be mounted concurrently by many EC2 instances/containers simultaneously — used for shared file access across a fleet (e.g. shared uploads directory across web server replicas). **S3** is object storage, accessed via HTTP API rather than a filesystem mount, and used for arbitrary file/blob storage, static website hosting, data lakes, and backups at virtually unlimited scale.

### 17. What is Auto Scaling, and what's the difference between scaling based on a target tracking policy vs. a scheduled action?
An Auto Scaling Group (ASG) automatically adds/removes EC2 instances to maintain a desired capacity, based on health checks and scaling policies. **Target tracking** (e.g. "keep average CPU at 50%") reactively scales in response to real-time observed load — the most common, self-adjusting approach. A **scheduled action** proactively scales at a specific, known time (e.g. scaling up before a predictable daily traffic spike, or scaling down overnight for cost savings) regardless of current metrics — useful when load is predictable in advance and you want capacity ready *before* it's needed rather than reacting after the fact (reactive scaling has inherent lag while new instances launch and become healthy).

### 18. What is EKS, and what does AWS manage versus what you still manage yourself?
EKS (Elastic Kubernetes Service) is AWS's managed Kubernetes control plane — AWS runs, patches, and scales the control plane (API server, etcd, scheduler) across multiple AZs for you. You remain responsible for the worker nodes (unless using EKS Fargate or managed node groups, which reduce but don't eliminate this), the CNI/networking configuration (commonly the AWS VPC CNI), IAM integration (mapping Kubernetes RBAC to IAM via `aws-auth`/EKS access entries), add-ons (CoreDNS, kube-proxy versions), and of course everything you deploy *onto* the cluster.

### 19. What's the difference between an Application Load Balancer's target group health check and an EC2 Auto Scaling Group's health check, and why might they disagree?
An ALB target group health check determines whether the ALB routes *traffic* to a specific target — a target failing this check is removed from rotation but not necessarily terminated. An ASG health check (EC2 status checks by default, or ELB health checks if configured) determines whether the ASG considers an instance healthy enough to *keep running at all* — a failing instance gets terminated and replaced. They can disagree if the ASG is using only its default EC2-status-check (which only detects instance/hardware-level failure, not "the application inside is unhealthy") while the ALB's target group health check is failing due to an application-level problem — the ASG won't replace the instance in that case unless you explicitly configure it to also honor ELB health checks, which is a common misconfiguration that leaves unhealthy-but-"EC2-healthy" instances running indefinitely.

### 20. How would you design a highly available, multi-AZ web application architecture on AWS from the ground up?
Public-facing ALB spanning multiple AZs, routing to an Auto Scaling Group of application instances (or ECS/EKS tasks) also spread across multiple AZs in private subnets, backed by an RDS Multi-AZ database (or Aurora, which is natively multi-AZ) for automatic failover, with static assets served from S3/CloudFront, and NAT Gateways in each AZ (not just one, to avoid a single NAT Gateway becoming a single point of failure for all AZs' outbound traffic) for private subnet internet access — health checks and Auto Scaling ensure the loss of any single AZ or individual instance is absorbed without manual intervention, and Route 53 health checks/failover routing can extend this to a full multi-region DR posture if the availability requirement goes beyond a single region.

### 21. What is the AWS Well-Architected Framework, and what are its pillars?
A framework of best-practice questions/guidance for evaluating cloud architecture across six pillars: **Operational Excellence** (running and monitoring systems, improving processes), **Security**, **Reliability** (recovery from failure, meeting availability requirements), **Performance Efficiency** (using resources efficiently as demand changes), **Cost Optimization**, and **Sustainability** (minimizing environmental impact). It's used both as a design checklist for new architecture and as a structured review framework (the "Well-Architected Review") for auditing existing workloads against these dimensions.

## Senior Level (5+ yrs)

### 22. Design a multi-account AWS strategy (AWS Organizations) for a growing company, and explain the reasoning behind account boundaries.
Use AWS Organizations with a landing-zone pattern (AWS Control Tower, or a hand-rolled equivalent): a dedicated **management/root account** (billing and organization-level policy only, minimal workload presence — a compromised or misconfigured management account is catastrophic, so it's kept as bare as possible), separate **workload accounts** per environment and/or team/product (dev, staging, prod separated by hard account boundaries, not just IAM within one account — an account boundary is a genuinely stronger blast-radius limit than IAM policy alone, since it also bounds resource limits, billing, and even a full account compromise), a dedicated **security/audit account** aggregating CloudTrail/Config/GuardDuty findings from every account (so an attacker who compromises a workload account can't also delete the audit trail of what they did), and a **shared services account** for genuinely cross-cutting infrastructure (a central CI/CD system, a shared container registry, Transit Gateway hub). Service Control Policies (SCPs) at the Organization/OU level enforce non-negotiable guardrails (e.g. "no region outside these three is ever usable," "CloudTrail can never be disabled") that apply even to account administrators, closing the gap that IAM policy alone (which even an account's own admin could modify) can't close.

### 23. Explain how VPC peering, Transit Gateway, and PrivateLink differ, and when you'd choose each for connecting multiple VPCs/accounts.
**VPC Peering** creates a direct, non-transitive 1:1 network connection between two VPCs (their CIDR ranges must not overlap) — simple and free of extra hourly cost, but doesn't scale well past a handful of VPCs since every pair needs its own explicit peering connection (no transitive routing through an intermediate peered VPC). **Transit Gateway** acts as a central network hub that many VPCs (and on-prem connections via Direct Connect/VPN) attach to, with transitive routing between all attached networks through one place — the right choice once you're beyond a handful of VPCs needing to communicate, since peering's N² connection growth becomes unmanageable. **PrivateLink** exposes a *specific service* (not a whole network) privately across VPC/account boundaries via an interface endpoint, without requiring any IP range compatibility, peering, or transitive routing at all — the right tool when you want to expose one specific application/API to consumers without giving them broader network-level access to your VPC, and is how many AWS managed services (and third-party SaaS) are consumed privately without traversing the public internet.

### 24. Walk through diagnosing and fixing runaway AWS costs discovered at the end of a billing cycle, and how you'd prevent a recurrence.
Immediate diagnosis: AWS Cost Explorer broken down by service/account/tag to find *what* actually grew, correlated against a timeline to find *when* it started (often correlates with a specific deploy, a misconfigured Auto Scaling policy stuck scaling up, an orphaned/forgotten resource — unattached EBS volumes, idle NAT Gateways, an unterminated load-testing environment, or a runaway Lambda in an infinite retry loop). Fix the immediate cause, then address prevention structurally rather than relying on someone noticing the bill later: AWS Budgets with proactive alerts well before month-end (not after), mandatory resource tagging (enforced via SCP/tag policies) so cost is attributable to the team/project that owns it — cost visibility by owner is what actually drives behavior change, not a central platform team chasing every team down after the fact — and automated guardrails (Config rules or scheduled Lambda cleanup) that catch/alert on the specific classes of waste you just found (unattached volumes, idle load balancers with no healthy targets) on an ongoing basis rather than as a one-time cleanup.

### 25. Explain how you'd design a disaster recovery strategy across AWS regions, and the tradeoffs between backup/restore, pilot light, warm standby, and multi-site active-active.
These represent an increasing spectrum of cost vs. recovery speed. **Backup & restore** (cheapest, slowest RTO — hours to days): back up data to another region and rebuild infrastructure from IaC only when disaster strikes. **Pilot light** (core infrastructure — a database replica, minimal always-on components — kept running in the DR region, everything else provisioned/scaled up on failover): faster RTO than backup/restore since the most time-consuming/stateful piece is already warm. **Warm standby** (a scaled-down but fully functional full copy of the environment always running in the DR region, scaled up on failover): faster still, since the application layer is already deployed and just needs scaling, not standing up from scratch. **Multi-site active-active** (full production capacity running in multiple regions simultaneously, all serving live traffic): near-zero RTO/RPO, but the most expensive and operationally complex (requires solving multi-region data consistency, which is often the genuinely hard part — not the compute/infrastructure side). The right choice depends on the actual business-defined RTO/RPO requirements for the specific workload, since active-active for a workload that could tolerate a 4-hour RTO is usually needless cost and complexity, not admirable rigor.

### 26. How would you approach securing and monitoring an AWS environment against both external attackers and insider/credential-compromise risk, at an organizational level (not just per-resource hardening)?
Layer detective and preventive controls: enable CloudTrail organization-wide with logs shipped to a separate, access-restricted security account (so an attacker compromising a workload account can't tamper with the evidence of what they did); enable GuardDuty (ML/threat-intel-based anomaly detection across CloudTrail, VPC Flow Logs, DNS logs) and Security Hub (aggregating findings across GuardDuty, Config, Inspector, and third-party tools into one place) organization-wide rather than per-account, since a threat actor moving laterally across accounts is exactly the pattern siloed per-account monitoring misses; enforce MFA for all human access (and increasingly, phishing-resistant methods over SMS/TOTP where feasible) and eliminate long-lived IAM access keys in favor of federated/SSO access and short-lived role assumption wherever possible, since long-lived credentials leaked (in a public GitHub repo, a compromised laptop) are one of the most common real-world initial-access vectors; and specifically monitor for and alert on the small set of highly sensitive actions that legitimate automation rarely performs but an attacker consolidating access commonly does (CloudTrail disabling attempts, root account usage, IAM policy attachment to a role granting broad new permissions, unusual cross-region API activity from a region you don't normally operate in) rather than trying to alert on everything indiscriminately, which just produces alert fatigue that trains people to ignore the signal.
