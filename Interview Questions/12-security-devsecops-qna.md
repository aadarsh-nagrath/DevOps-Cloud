## Junior Level (0–2 yrs)

### 1. What is DevSecOps, and how is it different from just "having a security team review things before release"?
DevSecOps integrates security practices and tooling directly into the DevOps pipeline itself — automated scanning, policy checks, and secure-by-default patterns applied continuously as code is written and shipped — rather than treating security as a separate, manual review gate bolted on right before release. The core idea ("shift left") is that catching a vulnerability during development/CI is far cheaper and faster to fix than catching it in a late-stage manual security review or, worse, in production — a manual pre-release gate alone also doesn't scale to organizations shipping many times a day.

### 2. What is the principle of least privilege?
Granting any identity (a person, a service, an application) only the minimum permissions it actually needs to do its job, nothing more — reducing the potential damage ("blast radius") if that identity's credentials are ever compromised or misused. It's a foundational security principle applied throughout IAM, network access, and application design.

### 3. What is a secret (in the DevOps security sense), and name a few examples.
A secret is any sensitive credential or value that grants access to something and must be protected from unauthorized exposure — API keys, database passwords, TLS private keys, cloud provider access keys, SSH private keys, OAuth tokens. Secrets should never be hardcoded in source code or committed to version control, and should be stored/injected via a dedicated secrets manager rather than plain configuration files.

### 4. What's the difference between encryption at rest and encryption in transit?
Encryption **at rest** protects data while it's stored (on disk, in a database, in S3) — protecting against someone who gains access to the underlying storage medium directly. Encryption **in transit** protects data while it's moving across a network (TLS for HTTP traffic, encrypted database connections) — protecting against someone intercepting/eavesdropping on network traffic. A secure system needs both — encrypting data at rest doesn't protect it while it's being transmitted, and vice versa.

### 5. What is a vulnerability scanner, and what's a common example used for container images?
A vulnerability scanner analyzes software (source code, dependencies, container images) against known vulnerability databases (CVEs) to identify security issues before they reach production. For container images, Trivy, Grype, and Snyk are common tools — they inspect an image's OS packages and application dependencies, flagging any with known, published vulnerabilities and their severity.

### 6. What is a CVE?
A CVE (Common Vulnerabilities and Exposures) is a publicly-disclosed, uniquely-identified security vulnerability in a specific piece of software, cataloged in a shared, standardized database — giving the industry a common reference (`CVE-2021-44228` for Log4Shell, for example) so different tools/vendors/teams can all refer to the exact same known issue unambiguously, along with an associated severity score (CVSS) indicating how serious it generally is.

### 7. What's the difference between authentication factors — something you know, something you have, something you are — and what is MFA?
"Something you know" is a password/PIN. "Something you have" is a physical/digital token (a phone receiving an SMS/push, a hardware security key, an authenticator app). "Something you are" is biometric (fingerprint, face). **MFA** (Multi-Factor Authentication) requires at least two different *categories* of factor together — a password alone, no matter how strong, is a single factor, and is considered insufficient on its own for anything security-sensitive, since it can be phished, reused from another breach, or guessed.

### 8. What is SAST, and what's a basic example of what it catches?
SAST (Static Application Security Testing) analyzes source code (without running it) to find security issues — hardcoded secrets, SQL injection-prone patterns (string-concatenating user input directly into a query), use of known-insecure functions/libraries. It runs early (often in CI on every pull request, or even in the IDE) since it needs only the source code itself, not a running/deployed application.

### 9. What is the principle of "defense in depth"?
Layering multiple, independent security controls so that if any single control fails or is bypassed, other controls still provide protection — rather than relying on one single strong barrier. A concrete example: even with a strong firewall, you'd still want authentication on internal services, encrypted data at rest, and monitoring/detection — because a firewall bypass alone shouldn't mean total, immediate compromise if the other layers are also in place.

### 10. What is a phishing attack, and why is it relevant to infrastructure/DevOps security specifically, not just "an email problem"?
Phishing tricks a person into revealing credentials or taking a harmful action (clicking a malicious link, approving a fraudulent MFA push) by impersonating a trusted source. It's directly relevant to infrastructure security because a successful phishing attack against an engineer with cloud console/CI/CD access can bypass nearly all of an organization's technical infrastructure controls in one step — many real-world major breaches began with a phished credential, not a sophisticated technical exploit of the infrastructure itself, which is why security awareness and phishing-resistant authentication (hardware security keys over SMS/app-based MFA) matter as much as technical infrastructure hardening.

## Mid Level (2–5 yrs)

### 11. What's the difference between SAST, DAST, and SCA, and where does each fit in a pipeline?
**SAST** (Static Application Security Testing) analyzes source code without executing it — runs earliest (PR/commit time), catches code-level issues but can produce false positives without real runtime context. **DAST** (Dynamic Application Security Testing) tests a *running* application from the outside, the way an attacker would (probing a deployed staging environment for actual exploitable behavior) — catches real, confirmed runtime vulnerabilities (including ones SAST can't see, like misconfiguration only visible when running) but requires a deployed environment and runs later in the pipeline. **SCA** (Software Composition Analysis) scans your dependencies (not your own code) for known vulnerable versions and license-compliance issues — critical given that the overwhelming majority of a typical application's code is actually third-party dependencies, not code the team wrote itself. A mature pipeline runs all three at the appropriate stage rather than relying on just one.

### 12. What is a secrets manager (Vault, AWS Secrets Manager, Azure Key Vault), and what capabilities does it provide beyond "an encrypted place to store passwords"?
Beyond encrypted storage, a proper secrets manager provides: fine-grained access control/audit logging (who/what accessed which secret and when), automated secret rotation (rotating a database password on a schedule without requiring a manual, error-prone process, and without an application outage during the rotation), and **dynamic secrets** (HashiCorp Vault's differentiator — generating short-lived, unique credentials on demand for each consumer rather than distributing one long-lived shared secret, so a leaked credential is valid for only a short window and is individually attributable/revocable) — capabilities that a simple encrypted key-value store or an environment-variable-based approach doesn't provide.

### 13. Why is committing a secret to Git (even in a private repository) considered a serious incident requiring rotation, not just deletion of the file?
Git preserves full history — deleting the file in a later commit does *not* remove it from earlier commits, which remain fully retrievable by anyone with repo access (or via `git log`/`git show` against any historical commit, or if the repo was ever public even briefly, potentially cached/scraped by external services and bots that specifically watch for exposed credentials). The only actually safe remediation is to treat the secret as permanently compromised and **rotate it** (issue a new credential, invalidate the old one) — rewriting Git history (`git filter-repo`, BFG) to scrub it is good hygiene for cleanliness but does not undo any exposure that already occurred, and should never be treated as a substitute for rotation.

### 14. What is container image scanning, and what's the difference between scanning at build time (CI) vs. scanning already-running images in a registry/cluster?
Build-time scanning (in CI, before an image is even pushed) catches known vulnerabilities before they're ever deployed, and can be configured as a hard, blocking gate (fail the build on a critical CVE). Registry/runtime scanning re-scans images that are *already* stored/deployed on an ongoing, scheduled basis — necessary because a container image itself doesn't change after it's built, but the *vulnerability database* does: a package that was "clean" the day an image was built can later be retroactively found vulnerable when a new CVE is disclosed, and only continuous re-scanning of already-deployed images catches that class of newly-discovered risk in images already running in production.

### 15. What is supply chain security, and what is an SBOM?
Supply chain security addresses risk introduced not by your own code, but by the components, tools, and processes that produce and deliver your software — a compromised dependency, a compromised build tool, a compromised CI pipeline, or a tampered artifact between build and deployment. An **SBOM** (Software Bill of Materials) is a structured, machine-readable inventory of every component (direct and transitive dependencies, their exact versions) that makes up a piece of software — enabling rapid, precise impact assessment when a new vulnerability is disclosed ("which of our hundred services actually use the vulnerable version of this library") instead of a slow, manual, error-prone audit across every codebase.

### 16. What's the difference between a network-layer intrusion detection system (IDS) and a runtime/host-based security tool like Falco?
A network IDS inspects network traffic for known attack signatures or anomalous patterns. **Falco** (and similar runtime security tools) instead monitors *system call and process-level behavior* on hosts/containers in real time (unexpected process execution inside a container, a container process attempting to open a shell unexpectedly, an unexpected outbound network connection from a process that never normally makes one) — detecting compromise/malicious activity that's already happening at the workload level, which network-layer inspection alone often can't see (particularly for encrypted traffic, or activity that never traverses the network at all, like a local privilege escalation attempt).

### 17. What is a Web Application Firewall (WAF), and what specific limitation should you be aware of when relying on one?
A WAF inspects and filters HTTP(S) traffic at L7, blocking known attack patterns (SQL injection payloads, XSS attempts) before they reach the application. The key limitation: a WAF is a compensating/defense-in-depth control, not a substitute for actually fixing the underlying vulnerability in application code — WAF rules can be bypassed by novel or cleverly-obfuscated payloads that don't match known signatures, and relying on a WAF as the *only* defense against, say, SQL injection (instead of using parameterized queries in the application itself) leaves a real, exploitable gap the moment an attacker finds a payload the WAF's rule set doesn't recognize.

### 18. What's the difference between security groups/network segmentation and application-level authorization, and why do you need both?
Network-level controls (Security Groups, NetworkPolicies, firewalls) determine *which systems can even attempt to talk to which other systems* — a coarse, connectivity-level boundary. Application-level authorization determines, *given* that a request has reached the application, whether the specific authenticated identity is actually permitted to perform the specific requested action on the specific resource — a much finer-grained boundary. You need both because network segmentation alone doesn't prevent a legitimately-connected, authenticated user/service from accessing data or performing actions beyond what they should be authorized for (an "insider" or a compromised-but-authenticated client is still inside the network boundary) — this is exactly the reasoning behind zero-trust's emphasis on not treating network location as a substitute for genuine per-request authorization.

### 19. What is a security incident response process, and what are its typical phases?
A structured, pre-planned approach to handling a confirmed or suspected security incident, typically following phases: **Preparation** (having tooling, runbooks, and trained responders ready before an incident, not improvised during one), **Detection & Analysis** (identifying and confirming an incident actually occurred, scoping its extent), **Containment** (limiting further damage — isolating affected systems, revoking compromised credentials — often split into short-term and longer-term containment), **Eradication** (removing the actual root cause — the malware, the vulnerability, the unauthorized access), **Recovery** (safely restoring affected systems to normal operation, with monitoring for recurrence), and **Post-Incident Review** (a blameless retrospective/postmortem capturing what happened and what should change to prevent recurrence — see the [Incident Response](../Incident%20Response%20and%20On-Call) notes in this repo for depth).

## Senior Level (5+ yrs)

### 20. Design a DevSecOps program for an organization that currently has security as a separate, late-stage manual gate. What's your rollout sequence, and how do you avoid it becoming "security theater" that developers route around?
Sequence matters for adoption: start with the highest-signal, lowest-friction automated checks integrated directly into existing developer workflows (secret scanning and dependency/SCA scanning on every PR, since these have low false-positive rates and catch genuinely serious, easily-understood issues) before introducing noisier or harder-to-interpret tooling (SAST with tunable rule sets, which needs calibration to avoid drowning developers in false positives that train them to ignore findings entirely). Make security findings actionable and owned by the team that can actually fix them (surfaced directly in the PR/IDE with clear remediation guidance, not a separate report emailed to a security team who then has to chase engineering teams down weeks later) — the single biggest determinant of whether a DevSecOps program becomes real practice or "security theater" developers route around is whether findings show up in the same workflow developers already use, with enough actionable specificity and low enough noise that acting on them is the path of least resistance rather than friction to escape. Graduate enforcement gradually — advisory/non-blocking findings first while the tooling and team are calibrating false-positive rates, moving to blocking gates only once the signal quality is trusted — introducing hard blocking gates before the tooling is trustworthy is exactly what causes developers to seek workarounds (self-approving, disabling checks) rather than genuinely engaging with the program.

### 21. Walk through how you'd respond to a confirmed leaked cloud credential (e.g. found in a public GitHub repo or a scanner alert) for a production AWS account, from the moment of detection.
Immediate containment first, investigation second — every minute a leaked credential remains valid is active risk: revoke/deactivate the specific credential immediately (deactivate the IAM access key, don't wait to "investigate first" since an active attacker could be using it right now). Then determine blast radius: check CloudTrail for any activity using that credential during the exposure window (what API calls were actually made, were any new resources created, IAM policies modified, data accessed/exfiltrated) — this determines whether it's "credential exposed, no evidence of misuse, rotate and move on" versus a genuine active-compromise incident requiring full incident response (isolating affected resources, checking for persistence mechanisms an attacker may have planted — new IAM users/roles, modified Lambda functions, new EC2 instances/security group rules — since a competent attacker establishes persistence quickly once they have access). Identify and fix the root cause of the exposure itself (why did a real credential end up in a public repo — missing secret-scanning pre-commit hooks, a developer testing locally with a real production credential instead of a scoped-down dev one) so the same exposure path doesn't simply recur. Finally, conduct a blameless post-incident review — the goal is fixing the systemic gap (secret scanning coverage, credential-issuance practices, dev/prod credential separation) not assigning individual blame, since punitive responses to security incidents reliably make people *less* likely to report the next one promptly.

### 22. How would you design a security architecture and process to satisfy a compliance framework (SOC 2, ISO 27001, PCI-DSS) without simply treating compliance as a check-the-box paperwork exercise disconnected from actual security posture?
The durable approach is to build compliance requirements as a natural byproduct of good technical practice already in place, rather than a separate parallel effort: access reviews and least-privilege enforcement (already good security practice) directly satisfy access-control requirements; centralized, tamper-evident audit logging (already valuable for incident response) directly satisfies audit-trail requirements; automated policy-as-code enforcement (already useful for consistency) directly satisfies configuration-standard requirements — when compliance controls are implemented as genuine engineering practice rather than a manual, periodic, compliance-team-only exercise, passing an audit becomes a matter of demonstrating existing, continuously-operating controls rather than a stressful annual scramble to reconstruct evidence after the fact. The trap to explicitly avoid is optimizing for "what will satisfy the auditor's specific checklist item" in isolation from "does this actually reduce real risk" — a classic failure mode is a policy that technically satisfies a compliance requirement's literal wording (a password rotation policy, for instance, which security research has increasingly shown can *reduce* real security by encouraging weak, predictable password patterns) while providing little or even negative genuine security value — a senior security-minded engineer should be able to distinguish and push back on that gap rather than treating every compliance requirement as automatically synonymous with good security practice.

### 23. What's your framework for prioritizizing which vulnerabilities/findings to actually fix first, given that no team can fix every finding from every scanner immediately?
Raw CVSS severity score alone is an insufficient prioritization signal — it doesn't account for actual exploitability in your specific context or real-world exploitation activity. A better framework combines: **actual exploitability and exposure** (is the vulnerable component reachable by untrusted input at all, or is it in a code path that's never actually invoked with attacker-controlled data — a "critical" CVE in an unused code path is a much lower real priority than a "medium" one directly reachable from an internet-facing endpoint), **known active exploitation** (CISA's KEV — Known Exploited Vulnerabilities — catalog and similar threat-intelligence sources indicating a vulnerability is being actively exploited in the wild right now, which should generally jump the queue regardless of its CVSS score alone), **blast radius if exploited** (a vulnerability in a service handling sensitive customer data warrants faster action than the identical vulnerability in an internal, low-value tool), and **remediation cost/complexity** (a one-line dependency version bump should simply be done immediately regardless of severity, given near-zero cost, while a finding requiring a significant architectural change needs to be genuinely weighed against other engineering priorities, not simply mandated on a fixed SLA divorced from real cost). Communicating this framework clearly to both engineering and leadership — rather than either treating every finding as an equal fire drill (which burns out teams and erodes trust in the signal) or letting a large backlog of unaddressed findings silently accumulate — is itself a core part of running a credible, sustainable vulnerability management program.
